# Day046「ねこ、光になる」v2 設計

設計日：2026-09-21。成果物はこの文書のみ。コード・既存仕様書・テストは変更しない。

## 目的と設計の前提

**指をスクロールする → 猫が加速して目の前の物を弾く → 飛散と衝撃を受け取る → 次はもっと大量に弾きたい、という循環を作る。** 操作の目的は従来どおり光速の99.999%への到達。回避、体力、買い物、別スコア、分岐を足さない。障害物は罰ではなく、加速の強さを見せる報酬とする。

初めての人が、開始後3秒以内に最初の干し草を弾き、説明を読み直さず加速を続けられることを狙う。UXの優先順位は、戦略＝加速の快感、要件＝衝突とスクロール、構造＝開始→加速→自動結果→再挑戦、骨格＝中央の猫と操作領域、表層＝輪郭・材質・音色の順。テスト件数だけを面白さの判定にしない。

## A. 物を弾き飛ばす手応え

**良くなること：景色を見るだけだった加速に、当てた瞬間と強さが分かる報酬が生まれる。**

### A1. 何を置き、何を壊すか

進行方向は現行どおり−Z、物体は+Zへ近づく。衝突対象は背景とは別の、猫の近くを通る3レーン（x=−1.25、0、+1.25 scene unit）に置く。scene unitは見た目用の単位で、表示km/hを実メートルに変換しない。

| 世界・速度範囲（km/h） | 衝突する3種類のテンプレート | 壊れ方／一体あたりの三角形上限 | 背景に残すもの |
| --- | --- | --- | --- |
| 牧場：0〜100未満 | 角形の干し草、木箱、短い柵 | 干し草60、木箱36、柵48。固まりが転がり、藁片／板片が2〜4個散る | 遠くの納屋・木・連続する柵 |
| 街：100〜1,000未満 | 看板、カラーコーン、小型の無人車 | 看板36、コーン32、車160。車は横転、板金片が散る | 建物・街灯。建物全体は倒さない |
| 空：1,000〜10,000未満 | 架空の気象ブイ、観測箱、氷塊 | ブイ96、箱48、氷塊40。外殻／氷片が飛ぶ | 雲。雲を金属のように壊さない |
| 軌道：10,000〜100,000未満 | 小型の無人衛星、パネル束、アンテナ枠 | 衛星144、パネル48、枠64。本体が回り、薄いパネル片が離れる | 地球・大気の縁・星 |
| 太陽系：100,000〜1,000,000未満 | 小惑星、氷隕石、無人探査機 | 岩80、氷80、探査機144。異なる大きさの塊になる | 太陽・惑星・環 |
| 星間：1,000,000以上 | 結晶隕石、黒い岩塊、架空の観測リング | 結晶64、岩80、リング96。多面体片が扇状に広がる | 星線。恒星・銀河そのものは壊さない |

車160の内訳例は車体12＋キャビン12＋窓8＋6角ホイール4×24＋灯火など32。各テンプレートは単一geometryに頂点色を持たせ、複数材質のグループを作らない。破片は全世界共通の12三角形の角片を色と縦横比で使い分ける。無人であることを造形で示し、キャラクター被害の表現は作らない。

衝突時は「元の位置に立っている物」をそのtickで必ず消し、同じ外観を飛翔状態へ移す。破片を足すだけで元の物が残る演出にはしない。車・衛星はまず形を認識できる本体が飛び、その後ろに破片が続く。最初の干し草は中央に固定し、入力を続けた場合に1.5〜3秒で接触する距離に初期配置する。

### A2. 当たり判定：距離順のキューと連続判定

三角形・Raycaster・物体間の総当たりを使わない。猫は進行レーンが固定なので、**各レーンの距離順リングキュー＋掃引した区間と簡易当たり領域の交差**で足りる。

1. 前進距離Sを倍精度の数値で持つ。各対象は到達距離s、半幅rx、半高ry、半奥行rz、種類、世代付きID、未衝突フラグを持つ。描画位置はs−Sから求め、背景の160 unit巻き戻しと切り離す。
2. 猫の当たり領域は固定の簡易箱（x=±0.45、y=0.2〜1.8、z=−0.35〜0.4）を基準とする。前面への到達距離には対象のrzを含める。顔・尻尾の個別メッシュは判定しない。高速の巻き込みだけ横幅を拡張する。
3. tickのS旧→S新が各レーン先頭の到達距離をまたいだら、x/yの区間重なりを調べる。距離が一致する場合も一度だけ命中。命中してもしなくても通過したIDをキューから外し、次を調べる。フレーム間で猫を飛び越えても取りこぼさない。
4. 命中時刻の割合α=(s−S旧)/(S新−S旧)も返す。飛散物は残り時間(1−α)dtだけ進め、衝突位置に一瞬戻る不連続を避ける。移動距離0のときは判定しない。
5. 各レーン4枠、未衝突対象は合計12個まで。可視先読みは最大4列、次の列までの時間を通常0.45秒以上確保。横幅で対象が当たらなかった場合はそのまま通過・返却する。

流れの基準は現行の `2＋45×min(1, log10(1＋v)/9)` unit/s を残し、上限47。停止時は衝突対象を止める。v=0.01未満も前進0とし、背景の待機演出とは分ける。次列の間隔は「その時点の流れ÷予定列数/秒」、最小1.4 unit。速度で列間隔を再配置せず、新たに足す列から適用する。

通常は1/60秒の固定tickで判定する。1tickあたり処理は最大12対象、全キュー補充も12枠以内。隠れタブからの復帰では経過時間を追いつかせず、既存同様に時計をリセットする。巨大dtがテストから来たときも固定tickへ分割し、描画の経過時間だけで衝突を回さない。計算量はO(3レーン＋通過対象数＋飛翔数)で、速度に比例する無制限な探索・生成を持たない。

世界の切り替えでは未衝突キューを作り直す。旧世界の飛翔物は0.12秒以内に縮めて返却し、その間は新世界の命中・追加飛散を抑制する。6世界分の飛散を重ねず、テンプレートの描画枠も再利用する。減速で前の世界へ戻った場合も同じ扱い。累計の速さの通過数には干渉しない。

### A3. 速度帯と飛び方

rは通常モーション時の定常目標命中数で、瞬間的な世界移行中まで保証する数ではない。各帯の中は対数速度で補間する。低速は中央だけ、高速は同じ列の左右も巻き込む。左右に当てる条件は、見える巻き込み環の半径と対象rxの和がレーン中心まで届くこと。見えない広範囲判定にはしない。

| 速度（km/h） | 命中量の目標 | 巻き込み半径x | 本体の初速 (外向きx, 上y, 後ろ+z) unit/s | 角速度／寿命 |
| --- | --- | --- | --- | --- |
| 0.01〜100未満 | 1列1個、0.5〜2個/秒 | 0.55 | (2〜3, 3〜4, 1〜2) | 3〜5 rad/s、1.2秒 |
| 100〜1,225未満 | 1列1〜2個、2〜5個/秒 | 0.55→1.1 | (4〜6, 4〜6, 2〜3) | 5〜8 rad/s、1.0秒 |
| 1,225〜27,600未満 | 1列2〜3個、5〜9個/秒 | 1.1→1.45 | (6〜8, 5〜7, 3〜4) | 7〜11 rad/s、0.9秒 |
| 27,600以上 | 1列3個、9〜15個/秒（最大5列/秒） | 1.45 | (8〜10, 4〜6, 4〜6) | 9〜14 rad/s、0.8秒 |

中央の本体の飛ぶ左右はIDから交互に決定。乱数はseed付きで±15%だけ足す。低速では衝突後80 msに潰れた形（進行軸0.75倍、横1.12倍）から戻し、高速ほどこの時間を40 msへ縮める。全体の時間停止は使わない。

地上・空の重力は−9.8 unit/s²、軌道以降は0。地上はy=0で一度だけ反発（係数0.25、水平速度0.6倍）し、その後滑らせる。飛翔体同士、地形メッシュとの衝突は行わない。位置は弾道式、姿勢は初期Quaternionと角速度で更新し、破片も同じ計算を使う。宇宙では慣性で回り続ける。

未衝突12＋飛翔本体12＝24個が本体の全世界共通上限。角片は64個、衝突環は12個（高速時の常時巻き込み環1個もこの中）。角片は低速2、高速4個/命中、寿命0.45〜0.8秒。最後の0.15秒で縮小して返却し、不透明材質のまま消す。上限時は最も古い飛翔本体／角片／一過性の環を返却してから追加。未衝突対象の枠は奪わない。

顔の前に本体が横切らないように、飛ぶx方向をカメラのスクリーン左右外向きへ補正する。投影した顔の周囲（顔の矩形＋上下左右12 CSS px）を飛翔開始後80 ms以降の本体が覆わない軌道をテンプレートごとに確認する。猫はdepthTestを維持し、常に最前面に描いてごまかさない。

### A4. 衝撃音・画面の揺れ

`ImpactEvent`にID、シミュレーション時刻、接触位置、材質、強さ、同じ列の命中数をまとめ、飛翔・音・揺れが同じイベントを消費する。描画だけのランダムな爆発音は鳴らさない。

| 材質 | Web Audioによる合成の初期値 |
| --- | --- |
| 藁・柔らかい外殻 | 生成ノイズ→lowpass 900 Hz、立上り3 ms、減衰90 ms。90→55 Hzの正弦波を小さく重ねる |
| 木 | bandpassノイズ中心1,400 Hz、Q=1.2、120 ms＋160→70 Hzの短い打音 |
| 車・金属パネル | ノイズ中心2,200 Hz、70 ms＋580 Hz/930 Hzの非整数比の正弦波2本、減衰180 ms |
| 岩・氷 | ノイズ中心1,800 Hz、150 ms＋120→60 Hzの打音。氷のみ3,200 Hzの小さいクリック |

ノイズは起動後にメモリ内で1秒分を生成して再利用。同時衝撃声部は4、同じ50 ms内の衝突は強さと件数をまとめ、トリガーは最大10回/秒。件数を足しても音量は平方根相当の増加と上限に止める。声用バスより衝撃用バスの上限を低くし、鳴き声中だけ衝撃を3 dB下げる。画面の命中から音の発音予約まで同じフレーム、実端末の知覚遅延は80 ms以内を目標とする。

1,225未満は即時の衝撃音、1,225〜27,600未満でも接触の衝撃音は即時とする。既存の0.75秒遅延は鳴き声だけの演出で、接触音には適用しない。27,600以上では衝撃音も鳴き声も停止し、予約済みを破棄。真空の表示と矛盾させない。最初の音速到達のboomは現行どおり1回だけで、その前後120 msの衝撃音をまとめて音量突出を防ぐ。

揺れはカメラやcanvas全体を動かさず、猫・HUDを除く世界ルートをカメラのright/up方向へ動かす。画面が衝撃を受けつつ`catScreen`の中央を維持できる。CSS px相当の振幅をカメラ距離とFOVからscene unitへ変換する。

| 速度（km/h） | 背景の最大振幅（390px幅時） | 減衰時間／発生上限 |
| --- | --- | --- |
| 100未満 | 横1.5 px、縦1 px | 80 ms、最大2回/秒 |
| 100〜1,225未満 | 横3 px、縦2 px | 100 ms、最大4回/秒 |
| 1,225〜27,600未満 | 横4 px、縦2.5 px | 120 ms、最大4回/秒 |
| 27,600以上 | 横3 px、縦2 px | 90 ms、最大4回/秒。連続振動にしない |

減衰正弦波は12 Hz、合成振幅を表の最大値に制限。回転・ズーム・全画面フラッシュは0。`prefers-reduced-motion: reduce`では揺れ0、猫の潰れ変形0、飛翔の移動量0.35倍、回転0.2倍、角片は各命中1個・全16個、環の拡大アニメーションを静止輪郭の120 ms表示に置換する。流れは既存の0.18倍を維持し、当たり判定も同じ遅い移動を使う。入力による速度・記録は通常と同じだが、衝突の頻度は低下する。動かない物に音だけ先行させない。

### A5. 描画予算と採否

本体は世界ごと3テンプレートをそれぞれ`InstancedMesh`で描く。待機と飛翔は同じバッチで、材質は頂点色対応の不透明な共通材質。角片は1バッチ、環は8分割・16三角形の1バッチ。各バッチの有効個数を詰め、`count`を設定する。見えない枠をゼロスケールにするだけでは提出三角形数は減らない。個体はCPUで可視判定してから詰め、動くインスタンスのバウンディングを古いまま使わない。

| Aの最大同時描画 | 三角形の計算 | draw call増分 |
| --- | --- | --- |
| 未衝突＋飛翔本体24 | 24×160＝3,840（最大テンプレートで保守的に計算） | 3 |
| 角片64 | 64×12＝768 | 1 |
| 環12 | 12×16＝192 | 1 |
| 合計 | **＋4,800** | **＋5** |

影マップ、ポストエフェクト、物理エンジンは追加しない。音は最大4衝撃声部＋1鳴き声＋1boomに固定する。負荷の最終合算はC4に記載。

捨てた案：三角形のメッシュ衝突は低ポリの見た目に対して計算の利益が小さい。汎用空間ハッシュは自由移動のない3レーンには過剰。速度をそのままscene unit/sに変換すると超高速で接触の前後が見えず、生成量も破綻する。建物の全面崩壊・破片同士の物理は予算外。画面中央を隠す大爆発と毎回のヒットストップは、顔の視認性とスクロール反応を損なうため採らない。

## B. 猫の鳴き声を猫に近づける

**良くなること：単なる電子音から、口が開いて母音が変わる、個性のある鳴き声に近づく。**

### B1. 実測値と、合成のための仮説を区別する

| 特徴 | 根拠となる数値・知見 | 設計への使い方 |
| --- | --- | --- |
| 成猫と子猫のF0・長さ | 成猫45匹の推定平均F0 593 Hz、長さ0.689秒。子猫9匹は1,238 Hz、0.488秒 | 基準声は600 Hz前後・0.7秒、子猫候補は1,200 Hz前後・0.5秒から試す。個体の全範囲を示す値ではない |
| F0の範囲と時間変化 | 2匹12発声の選定標本はF0の最小418〜最大1,003 Hz、長さ0.27〜1.13秒。上昇／下降の輪郭が文脈で異なる | 全てを同じ山型と断定しない。今回は短い立上り→中盤ピーク→下降を演出として選ぶ |
| F1・F2 | 別の成猫6匹・84発声の表3で、個体ごとの平均F1は1,395.8〜1,751.9 Hz、F2は2,643.1〜3,039.2 Hz | 共鳴の出発点はF1約1,500、F2約2,800 Hz。F0の2倍・3倍と混同しない |
| 「ニ→ャ→ー」 | 猫が日本語の音節を発音するわけではない。狭い口から開口して閉じる音色変化を、人が母音に似て聞く | 「ニ」の高域／鼻音→「ャ」の開口→「ー」の減衰、を以下のフィルター遷移に対応させる |

F0・長さの最初の行は音声学の学会報告 [Schötzほか、FONETIK 2019、表5](https://roberteklund.info/pdf/Schotz_vandeWeijer_Eklund_2019_Meowsic_PhoneticVocalisationStudies.pdf)、時間変化と範囲は録音・聴取実験 [Schötz & van de Weijer、FONETIK 2014、表1・図1](https://lucris.lub.lu.se/ws/files/3057285/4882308.pdf) による。F1/F2は査読誌の録音解析 [Schalzほか、2021、表3（論文PDF）](https://pdfs.semanticscholar.org/d15a/535786dc7e59c0854957f370808ec707df7f.pdf) による。これらは標本の測定結果で、全ての猫に共通する規格ではない。

口の形と母音らしい知覚の関係は、声道模型と合成音の知覚を扱う [Ekströmほか、VIHAR 2024](https://portal.research.lu.se/en/publications/a-single-formant-explicates-the-ubiquity-of-meow/) も参考にする。ただし人間の母音表をそのまま猫の実測値として採用しない。特に以下のF3・鼻音・Q・遷移時刻は**本設計の試聴用初期値**であり、論文で実証された猫の固定値とはしない。

### B2. 選ぶ方式とノード構成

方式は**倍音を含む1音源＋時変フォルマント**。最初の推奨候補は下記P2だが、採用音色は依頼者の試聴で決める。倍音のない正弦波にピーキングフィルターを掛けても、存在しない帯域の音は生まれないため、現行2本にEQを足すだけでは済ませない。

基本経路は、`OscillatorNode`（`PeriodicWave`で倍音源）→音源Gain→`BiquadFilterNode`のpeakingを直列に2〜3段→lowpass→発声包絡Gain→voice bus→masterとする。音源の第n倍音振幅はnの−1.3乗（1〜24次、DC=0）を初期値にし、ブラウザの帯域制限に加えて最終lowpass 6,000 Hzで耳障りな成分を抑える。発声ごとのランダムな位相変更はしない。

F0は低速P1/P2で時刻比0 / 0.18 / 0.55 / 1.0に対し **480 / 680 / 610 / 430 Hz**。各点間を指数ランプでつなぐ。弱い揺らぎは5 Hz・±8 centの値曲線をdetuneへ予約し、常時LFOノードは使わない。音量は10 msで立ち上げ、0.2D付近を最大、末尾60 msで0へ。Dは発声長。ノイズは発声中のRMSで有声音の−32 dB、冒頭のみ−24 dBを上限に足す。

| 時刻比t/D | 音色の狙い | F1 / F2 / F3（Hz） | 初期peaking設定 |
| --- | --- | --- | --- |
| 0〜0.12 | 狭い口・短い「ニ」 | 1,200 / 3,000 / 4,500 | F1:+9 dB,Q4、F2:+7 dB,Q5、F3:+4 dB,Q5 |
| 0.12〜0.35 | 開口して「ャ」 | 1,700 / 2,700 / 4,100へ移る | 同じgain/Q |
| 0.35〜0.75 | 開口を保つ「ー」 | 1,600 / 2,800 / 4,200へ緩やかに移る | 同じgain/Q |
| 0.75〜1.0 | 口を閉じて減衰 | 1,200 / 2,600 / 3,900へ移る | F1/F2 gainを末尾で3 dB下げる |

表の数値は経由点であり、段差切替にしない。帯域幅の概算は中心周波数/Qだが、peakingの実際の形はgainにも依存するので後述の周波数応答で確かめる。F0を上げてもフォルマントを同じ倍率で動かさず、音源と声道の役割を分ける。

P2の鼻音は同じ倍音源から分岐し、bandpass 650 Hz・Q2・gain最大0.12と、口側のnotch 1,100 Hz・Q3を冒頭0.10Dだけ使い、その後クロスフェードして消す。猫の鼻腔の厳密な再現ではなく「閉じた口から開く」対比の調整用とする。副音源のうなりはF0/2の正弦波、主音源振幅の0.05、0.2D〜0.6Dだけ。声の主たるF0を半分に誤認させない強さに止める。

masterに共有の`DynamicsCompressorNode`を置く（初期値threshold −12 dB、knee12 dB、ratio4、attack3 ms、release100 ms）。これは完全なリミッターではない。ゲイン側でも最悪同時発音のピークを抑え、実レンダーで確認する。各発声のgain/filterも終了・停止時に切断し、sourceだけを止めて枝を残さない。APIのノード・時間予約・オフライン描画は [Web Audio標準仕様](https://www.w3.org/TR/webaudio/) に従う。

### B3. 依頼者に聴いて選んでもらう3候補

| 候補 | ノードと違い | 音の狙い／懸念 |
| --- | --- | --- |
| P1：成猫・輪郭重視 | Oscillator1、peaking2本（F1/F2）、lowpass1、ノイズ用highpass1。基準D=0.72秒、上記F0。鼻音・副音源なし | 簡潔な「ニャー」。聞き取りやすいがシンセらしさが残る可能性 |
| P2：成猫・鼻音とうなり（推奨） | Oscillator2（主音源＋F0/2）、peaking3本、lowpass1、鼻音bandpass1、notch1、ノイズhighpass1。基準D=0.72秒 | 冒頭の鼻音と中盤の厚み。電子音の単調さを減らすが、強すぎると唸り声・人声になる |
| P3：子猫・軽さ重視 | Oscillator1、peaking3本、lowpass1、ノイズhighpass1。F0経由点1,050/1,350/1,200/950 Hz、D=0.50秒。表のF1〜F3を1.15倍、Qを0.8倍 | 小さく高い鳴き声。かわいさを狙うが高音が刺さる、玩具に聞こえる可能性 |

P1はBiquad計4、P2は7、P3は5。全候補にノイズ用BufferSource1、発声包絡Gain等を使う。最も多いP2でも声はOscillator2＋ノイズ1まで。同時に鳴く猫は1匹分に限定し、次の声を際限なく重ねない。

将来の実装時には、同じローカル画面の開発用試聴入口からP1/P2/P3を順番を伏せて再生できるようにする。公開ゲームに音色選択モードは追加しない。比較は単発低速、街相当、音速直前の3条件、各3回。候補ごとのRMSを±1 dB以内にそろえ、同じ端末・音量で比べる。スマホ内蔵スピーカーとヘッドホンで「猫に聞こえる／電子音・人声に聞こえる／繰り返すと疲れる」を依頼者に選んでもらう。全候補不採用も可能とする。

この依頼は設計だけなので音声はまだ生成していない。P2を「猫に聞こえた」とは扱わず、試聴採用をBの完了条件にする。

### B4. 速度帯ごとの声と予約

| 速度（km/h） | 発声開始間隔 | P1/P2のD | F0倍率 | 発音 |
| --- | --- | --- | --- | --- |
| 0.01〜100未満 | 3.2→2.4秒 | 0.72→0.64秒 | 1.00→1.08 | 即時 |
| 100〜1,225未満 | 2.4→1.5秒 | 0.64→0.52秒 | 1.08→1.20 | 即時 |
| 1,225〜27,600未満 | 1.5→1.0秒 | 0.52→0.42秒 | 1.20→1.30 | 口の動きから0.75秒後 |
| 27,600以上 | 発声予約なし | — | — | 既存の予約を含めて無音 |

帯内は対数補間、境界で連続にする。P3のDは表のD×0.50/0.72、F0倍率は上限1.15とする（最も高い経由点でも約1,553 Hz）。速度で声道まで極端に小さくしない。口は発声予定のt/Dで開閉し、固定の「0.3秒だけ頭全体を縦に伸ばす」処理をやめる。遅延帯でも口を先に動かし、音だけが遅れる。

発声プランは口の開始時に固定。キューは再生中1＋予約1までとし、減速で音の予定が交差したら後の発声をずらす。世界変更だけでは鳴き直さない。ミュート、真空への到達、再開始、blur、hiddenでvoice/impact/boomの予約とノードを停止し、復帰時に古い音を再生しない。`AudioContext`が未解除・resume失敗でもゲームは進む。

### B5. 耳を使わずに確認する指標

44.1 kHzと48 kHzの`OfflineAudioContext`で本番と同じグラフ・seed・プランを描画する。設定値を読むだけで合格にせず、実PCMも測る。検証用の解析はテスト内に閉じ、新しいランタイム依存を増やさない。

| 指標 | 方法と合格条件 |
| --- | --- |
| 無音・異常値 | 全sample有限。発声区間RMSは−32〜−14 dBFS、peak≤−3 dBFS。実ゲイン込みの基準。完全無音・DC偏り（平均絶対値>0.01）は不合格 |
| F0軌跡 | 40 ms窓・10 ms hopの自己相関で追跡。有声フレームの90%以上が予定F0の±5%以内。冒頭/末尾各30 msは除外。P2のF0/2への誤追跡を別集計し、10%超なら副音源を弱める |
| フォルマント | 各経由点のfilter設定を凍結し、広帯域ノイズを通したスペクトル包絡と`getFrequencyResponse`を両方測る。F1/F2（P2/P3はF3も）の局所ピークが狙いの±10%または±100 Hzの大きい方以内。声のFFT最大ビンをそのままフォルマントと呼ばない |
| 実際の声の共鳴 | 音源単体と最終声のスペクトル比を比較し、F1/F2近傍の倍音エネルギーが隣接谷より3 dB以上強い。高F0で共鳴の間に倍音がない場合は、ピーク位置の断定をせず上段の伝達特性で検証 |
| 発声長・包絡 | 10 ms RMSが−50 dBFSを超える開始〜終了を計測し、予約Dとの差±40 ms。境界に不連続なクリックがないことを末尾20 msのエネルギー減衰でも確認 |
| 時間・停止 | 即時／0.75秒遅延は予約誤差±1 audio render quantum、連続10発声で予約枠超過0。ミュート／真空到達後20 ms以内に出力RMS<−80 dBFS。即時停止前に5〜10 msのgain rampを使う |
| 最悪の重なり | 鳴き声1＋衝撃4＋boom1を重ね、有限・peak<0 dBFS、定常ノード数へ戻ることを確認。100回繰り返して生きたノード数が増えない |

これらは合成の再現性と破綻の検出であり、「猫に聞こえる」の自動認定ではない。

捨てた案：正弦波2本＋グライド継続は倍音と声道変化が足りない。単純FMは安価だが金属的な側帯波を猫らしく調整しにくい。声道の管モデル／非線形声帯モデルは有望でも、今回の端末負荷・実装規模・較正データに対して重い。録音・学習済み音声モデル・外部サンプルは枠外。3本のフォルマントが必ず2本より良いとは決めつけず、P1も同条件で聴く。

## C. 猫と世界のモデルを作り込む

**良くなること：顔とシルエットで猫だと分かり、速さによって走り方も景色の材質も変わって見える。**

### C1. 優先順位は顔と耳 → 胴体の輪郭 → 尻尾 → 脚

現行の球を全て細分化するのではなく、画面に残る顔と輪郭に三角形を使う。外部テクスチャなしの、造形が読めるスタイライズを目標にする。

| 部位 | 作り込み・生成方法 | 現行に対する追加三角形の予算 |
| --- | --- | --- |
| 頭・頬・口元 | 頭の経緯分割を16×10から24×16へ（288→720、差432）。頬の頂点を外へ、口吻を前へ出し、球の輪郭から猫の頬・顎へ。分離した下顎と左右の口吻を含める | ＋900以内 |
| 目・鼻・耳 | 眼球の大球化ではなく上瞼・縦瞳孔・小さなハイライト。耳は4角錐から、厚みと内側の窪みを持つ独自三角形メッシュへ。顔の左右を同じ高さにしすぎない | ＋300以内 |
| 胸・肩・腰 | 球の継ぎ目を埋める輪郭へ頂点調整。首下の白い毛・縞は頂点色で付け、箱の縞を浮かせない。肩と腰を別の可動Groupにする | ＋600以内 |
| 前後脚・肉球 | 肘／膝と足先の2関節。追加球を積まず、既存脚の三角形を配分し直す。接地側の足先を平たくする | ＋400以内 |
| 尻尾・ひげ | 5つの球を8角断面×12区間の先細り管へ置換（側面192＋端面16）。制御点6個で滑らかな曲線にし、既存の6本のひげも顔と一緒に統合 | ＋200の予備枠。通常は差引減 |
| 合計の上限 | 削減分を他部位への無制限な追加に流用しない | **＋2,400** |

猫は既存の生成引数と`cat/head/paws/tail/coatMaterials`相当の参照を維持し、既存テストの意図を残す。追加ライブラリのmerge utilityは導入せず、生成頂点・法線・色・indexを同じ静的部位内で一つの`BufferGeometry`へまとめる。動く顎・脚・尻尾は別Groupを維持する。頂点色と共通材質で色違いのMeshを増やさず、猫のdraw call純増は4以内。

光速演出でも目・鼻は暗く、顔の毛色は読み取れるままにする。現行のemissive上限0.16、白化0.18、halo opacity0.24、halo scale1.18を上回らない。発光で造形を隠して品質向上としない。光の尾の根元が実尻尾より0.2以上低く、猫の境界内にある既存の関門も維持する。

### C2. 走りと姿勢

| 速度（km/h） | 姿勢・走りの初期値 |
| --- | --- |
| 100未満 | 1.8→3歩行周期/秒。肩と腰を逆位相で±3°、胴体上下0.02〜0.04 unit。足が着く約35%の区間は足先yを固定して滑りを減らす |
| 100〜1,225未満 | 3→4.2周期/秒のギャロップ。前後脚の位相差を0.35周期、左右差を0.08周期。前傾最大8°、腰が蹴ってから胴体が伸びる |
| 1,225〜27,600未満 | 4.2周期/秒を上限にし、残りは前傾12°・伸びた姿勢で速さを見せる。脚の振幅は徐々に半分。耳を後ろへ10〜18° |
| 27,600以上 | 0.4秒で脚を後ろへ揃える飛翔姿勢。無限に高速な足振りをしない。尾が後ろへ流れ、肩の小さい呼吸だけ残す |

身体の進行軸伸長は現行の「body.scaleとcat.scaleの二重伸長」をやめ、胴体ローカル最大1.18倍にまとめる。頭は胴体の伸長を継承しない。尻尾は胴体の変化へ100 ms遅れて追従。頭は現行のカメラ向きのyaw −0.8 radを基準に、胴体前傾を打ち消して顔を見せる。視線がカメラから外れる角度は±8°以内を狙う。

`prefers-reduced-motion`では上下動・肩腰の揺れ0、脚振幅0.2倍、姿勢の遷移は緩やかに0.4秒。衝突で猫本体を画面外へ押し出さない。時間は共有シミュレーション時計を使い、描画FPSで足の速さが変わらないようにする。

### C3. 世界ごとの印象を変える場所

以下は背景だけの追加枠で、Aの飛ぶ物を二重計上しない。6世界を同時に描かないため、加算するのは最大の1世界分。

| 世界 | 足す／直す点 | 追加三角形の内訳と上限 |
| --- | --- | --- |

| 街 | 建物の奥まった入口、屋上縁、張り出し。窓は形を増やすより頂点色で階ごとの反復。歩道と縁石で道路の尺度を作る | 建物詳細12×120＋歩道16×36＋灯り・影用288＝**2,304** |

各世界の不透明な静的形状は最大4バッチの追加枠でまとめる。接地影は外部画像を使わない頂点色の平面・最大24三角形を1枚、影用ライトやshadow mapは使わない。地上の猫が浮いて見えない程度の弱い影とし、追加4 draw callの中に含める。

遠景の色だけでなく「手前に識別できる物、奥に世界の象徴」を作る。ただし画面中央の顔の背景には高コントラストな窓列・星線を重ねない。別世界のcrossfadeを重ねて描く方式は採らず、色の遷移と単一世界の切替で済ませる。

### C4. AとCを合算した負荷の上限

| 区分 | 三角形の計画値 | draw callの計画値 |
| --- | --- | --- |
| 現状の観測上側を仮基準にする | 7,000 | 49 |
| C：猫 | ＋2,400 | ＋4以内 |
| C：背景（街が最大） | ＋2,304 | ＋4以内 |
| A：衝突本体・破片・環 | ＋4,800 | ＋5 |
| 合計 | **16,504** | **62以内** |
| 調整余地込みのハード上限 | **18,000** | **64** |

18,000は約2万より低く、現状を6,000と見ても3倍を越えない値。数値は設計予算で実測結果ではない。現在の35〜49 calls／6〜7千が全世界・全視点の最悪値とは限らない。特にInstancedMeshを大きくまとめると、以前は個別にカリングされていた遠景まで提出されるので、単にこの表の加算だけで合格にしない。

実装では絶対予算も持つ：**猫本体8,300、背景と既存の光の尾・halo・地上影の合計3,404、Aの4,800、予備1,496＝18,000**。この内訳を超える世界は遠景の個数・分割数を減らす。猫の8,300は現行の球中心の形状約5,900＋2,400に対応する概算。線は三角形数に含まれないので、星も現行180本を上限に別計数する。

背景は奥行き区画ごとにCPUで可視判定して有効instanceだけを提出し、1世界分を巨大な常時描画バッチにしない。画面外を除いた後の`renderer.info.render.calls/triangles`を測る。影・ポスト処理なし、DPR上限1.5を継続。

実機は390×844と390×664相当のiOS Safari・Android Chromeで各世界30秒以上、最多破片・鳴き声・HUD同時更新を含める。目標は60 fps、最低条件は95%のフレーム間隔33.3 ms以内、可視状態で200 ms以上の停止なし。これはCPU時間だけの測定では代用できない。未達なら、DPR1.0→破片64から32→遠景個数半減の順で落とす。品質状態は保存しない。中央の衝突、入力感度、顔を先に削らない。

捨てた案：毛を1本ずつ作る、全メッシュの分割数倍増、PBR画像・外部モデル導入は予算・制約に合わない。骨格と皮膚を備えた写実モデルは今回の形状生成量に対して重い。色付きの球だけを増やす方法は物の識別を改善しにくい。固定顔の維持を優先し、大きいカメラ周回・激しいズームも採らない。

### C5. 猫を中央に置き、顔を見せる関門

既存の`catScreen`の意味は猫の実メッシュ（尾を含む）を投影した境界で維持する。光の尾・halo・飛散は除外するが、耳・足先を除外して合格させない。

- x中心0.40〜0.60、高さ0.18〜0.38、左右上下すべて0.02〜0.98の内側。既存3画面サイズと既存9速度点を維持する。
- 追加で、各姿勢の歩行周期12位相、衝突から0/40/80/160 ms、resize直後、reduced-motionの両方を検査する。
- カメラは現行の向き・FOV49°を出発点とし、モデル完成時に最大姿勢の投影から距離とlookAtを調整。最大投影高0.30〜0.34を狙い、瞬間変形にも余白を残す。毎フレームの自動ズームはしない。
- `catScreen`の箱だけでは顔の向き・遮蔽を証明できない。左右眼の位置、鼻、顔前方ベクトルを検証用に返し、顔前方とカメラ方向の内積>0.5、眼鼻が画面内、顔高さがスマホで24 CSS px以上を追加目安にする。最後は同じ速度点の実画像で両眼・鼻・耳を確認する。

## D. スマホは指のスクロール量で加速

**良くなること：指を送った量が加速の手応えになり、指を離して持ち替えながら最後まで遊べる。**

### D1. 採用する入力とページ移動の両立

加速に使うのは**画面上を指で上下に送る量**。ページの`scrollTop`は使わない。上下どちら向きでも加速し、方向の違いは減速に割り当てない。主操作を「猫の画面を上下にスクロール」と表示する。

| 領域 | 役割とCSS/イベント方針 |
| --- | --- |
| プレイ中のscene左側〜右端44 CSS px手前 | 透明な入力面。Pointer Eventsの`pointermove`で指のclientY差を取る。`touch-action:pinch-zoom`で1本指のページpanを抑え、ピンチは許す |
| scene右端の幅44 CSS px | canvasの子ではない兄弟の「ページ移動帯」。矢印と「ページ」を表示。`touch-action:pan-y pinch-zoom`、イベントを奪わずページをネイティブスクロール |
| 見出し・速度パネル・速報・余白・footer・共有欄 | 通常のページスクロール。加速しない。共有ボタンのclick/タッチは従来どおり |
| 開始前・結果表示中 | 加速用入力面を無効化。結果内スクロールと共有・再挑戦の操作が優先 |

390px幅でappが362pxなら、入力面318pxとページ移動帯44pxになる。猫の3D描画範囲はscene全幅のまま、ページ移動帯はその端に重ねる。猫を左へ寄せず、中央条件を保つ。ヒントは「上下にスクロールで加速／右端の↕でページ移動」。右端のラベルに隠れるHUDは内側へ余白を取る。

入力面とページ移動帯は`touch-action:none`の祖先で包まない。現行canvasの全域`touch-action:none`は外し、pointerの所有者を決める面だけで制限する。ジェスチャー開始後の`touch-action`変更では、その操作のネイティブpanを後から許可できないため、開始領域で用途を固定する。[Pointer Events標準仕様：touch-action](https://www.w3.org/TR/pointerevents3/#the-touch-action-css-property)

1本指が入力面で始まったらpointer captureし、その指を上まで送っても加速操作を維持。右端へ途中で横切ってもページ操作へ切り替えない。ページを動かすときは指を離し、右端かscene外から新しい操作を始める。ページ移動帯で始まった指がsceneへ入っても途中から加速しない。この制約は同じ上下ジェスチャーの誤判定を防ぐために受け入れる。

document/bodyの`overflow:hidden`や全ページ`preventDefault`は使用しない。2本目の指、pointercancel、lostpointercaptureではゲーム入力を解除し、ピンチズームを邪魔しない。Touch EventsとPointer Eventsを二重登録して移動量を倍にしない。イベントを処理するのは入力面だけとする。

### D2. 移動量から推力を作る純関数

将来の`lib/input.js`にはDOMを読まない計算を置く。入力は「正規化済みの上下移動量、経過秒、前のバッファ状態、解除理由」、出力は「新しいバッファ状態、推力u（0〜1）、表示用の入力中フラグ」。DOMのclientY・時刻・領域判定は`app3d.js`側のアダプターが担当する。

**移動量の正規化**：clientYの差の絶対値（CSS px）×440/入力面の高さ。高さは290〜540にclampする。短い画面でも同じ割合の指移動ならほぼ同じ加速量になる。pointerdown時の座標は基準を置くだけで加速しない。横移動だけは0。震えのデッドゾーンはストローク開始から累積4 CSS pxとし、それを越えた後の細かいイベントを1件ごとに捨てない。

距離を直接一回の速度増分にせず、**最大0.45秒分の推力バッファQ**へ入れる。入力距離dに対しd/180秒を追加し、0.45秒で打ち止め。シミュレーションの経過dtごとにdtを消費する。Q≥0.08秒ならu=1、0<Q<0.08ならu=Q/0.08、0ならu=0。0.08秒の末尾だけ滑らかに減る。時間と距離の順序はイベントのtimestamp順に処理し、固定tickの間の消費も同じ時計で積分する。

この短いバッファは慣性スクロールをゲーム側で模すもの。指を離しても最大450 ms以内に推力0へ戻るので、持ち替えの小さい隙間が即減速にならない。溜められるのは一瞬だけで、連打で数秒分の加速を貯めることはできない。無移動の押しっぱなしではQは増えない。残量は既存の操作ヒントの細いバーで返し、新しい主ボタンは増やさない。

数値例：標準高さで正規化距離120pxを0.4秒で送ると0.667秒分を供給できる。指の持ち替え0.15秒込みでも、平均供給は180px/秒を上回り、暖機後はu=1を維持できる。これは約90秒の現行最大加速経路へ到達可能な入力である。最後の光速付近ではほんの少しの減速でも遠ざかるため、u=1を維持できることを必須にする。

イベントを60回に分けても1回にまとめても、同じ時刻軌跡・距離なら同じQを得ること。イベント間の経過が250 msを越えた場合は座標の飛びとして基準を置き直し、古い位置から巨大な距離を足さない。複数coalesced eventを使う場合は外側eventの距離を重ねて加算しない。入力状態は保存しない。

### D3. 推力と既存物理式の接続

u=1は今の押しっぱなし、u=0は今の減速と一致させる。0<u<1はその間の加速度にする。vはkm/h、tは秒、cは現行の光速定数とする。

- v<0.9c：dv/dt = {0.32u − 0.7(1−u)} × (v＋0.05)。係数をkとすると、区間内の解はv新=(v旧＋0.05)exp(k dt)−0.05。
- v≥0.9c：dv/dt = 0.55u(c−v) − 0.7(1−u)(v＋0.05)。a=0.55u＋0.7(1−u)、b=0.55uc−0.035(1−u)と置き、区間内の解はv新=b/a＋(v旧−b/a)exp(−a dt)。
- 0.9cを横切る時間で区間を分ける。vの下限0、上限c×0.99999、自動結果、γ積分の意味は維持する。変化するuは固定tick内のバッファ境界で分割する。

入力の純関数はQ/u、物理の純関数はv/u/dtから速度または加速度を返す責務にする。特にu=1を真偽trueの現行計算と比較し、ゴール到達時間を不用意に変えない。速度・表示・衝突の時間を別々のタイマーで加速させない。

### D4. PCと、入力を止めたとき

PCはマウス左ボタン長押し・Space/Enterを残す（u=1、離せば即u=0）。ゲーム面上のホイールも同じスクロール加速に対応。ホイールはフォーカスがゲーム面にあるプレイ中だけ受け、右端・scene外・結果の上では常にページに渡す。フォーカスがない場合は最初からページを動かす。キー処理はdocument全体を無条件に奪わず、ゲーム／開始／再挑戦にフォーカスがあるときに絞り、リンク・フォーム・ミュートを邪魔しない。

`wheel.deltaMode`はpixelをそのまま、lineは16 CSS px/行、pageは入力面の高さに換算し、D2の距離へ正規化する。wheelでページpanを止めるのは受理したゲーム面のイベントだけ（`passive:false`）。ctrl/meta付きはズームとして通す。OSのトラックパッド慣性wheelは物理的に指を離した時刻を判別できないので、届いたイベントを入力として扱い、最後のwheelから450 ms以内に停止する仕様とする。

複数入力は加算せず最大のuを採る。キーボード／マウス長押しを始めると古いQを捨て、長押し中はスクロールのQを貯めない。これにより離した後に隠れた残量が出ない。押下・移動した最初のユーザー操作でAudioContextを解除する。

| 停止・中断の理由 | 挙動 |
| --- | --- |
| 指が止まる／離れる | 新しい距離が入らなくなり、Qを消費。最長450 ms後に推力0、以後は既存の減速 |
| 右端かscene外からページスクロールを始める | ゲーム入力・Qを即時解除。共有へ移動中は加速しない |
| pointercancel / lostpointercapture / blur / hidden / 2本指 | 即時解除、Q=0。隠れた時間を後で進めない。音予約も破棄 |
| 結果・再挑戦・WebGL消失 | すべての入力ID・Q・予約をリセット。持ち越しで再加速しない |
| OSの画面回転・リサイズ | 接触中の入力を解除し、寸法を取り直す。clientYの変化を距離に数えない |

捨てた案：ページ全体のscrollTopを使うと末端で加速できず、共有操作も加速になる。canvasの縦スクロールを毎回奪うだけではページ脱出できない。上は加速／下はページ移動という方向分割は往復入力と衝突しやすい。長押しで「ゲームモード」に入る方式はスマホの希望から外れ、主アクションも増える。タッチとホイールを無条件にdocumentで捕まえる方式も採らない。

## 実装時の境界と検証計画

### 責務と更新順

将来の変更候補は`lib/input.js`（新規の純粋な入力計算）、`lib/impacts.js`（新規の配置・掃引判定・飛翔状態）、既存のscene/sound/audio-state/physics/game/app3dと表示文言。ファイル分割自体を目的にせず、実装時もこの範囲で収める。

固定tickの順序は「入力を時刻順に消費→速度とrunを更新→世界を決定→衝突と飛翔を更新→音／口／揺れのイベントを配信→結果処理」。描画は確定状態を読むだけにする。`advance(ms)`もこの同じtickを使う。現在はscene.drawのdtで背景と足が進むため、そこにだけ衝突を追加すると手動advanceでは飛散が進まない。これを先に分離する。

`window.__day046.snapshot()`は既存項目を維持し、入力u/Q、衝突累計、直近ID/材質、待機・飛翔・角片・環の個数、描画予算、顔の投影を追加する。検証用の入力入口はtimestamp付き正規化サンプルを本番と同じ入力関数へ渡す。速度や命中数だけを書き換えて成功を作らない。

| 対象 | 実装時に確認すること |
| --- | --- |
| A：純ロジック | 1tickで対象を跨ぐ、大きいdtの分割、複数列、境界ちょうど、巻き込み外、同ID二重命中0、再利用したIDの世代、世界切替、上限飽和。seed固定で30/60/120 Hz相当の結果を比較 |
| A：実挙動 | 低速では1個の接触→消失→飛翔→衝撃音が対応。高速では1列3個が飛ぶ。初回接触3秒以内。無音境界とreduced-motionに矛盾しない |
| B | B5のPCM検証と、P1/P2/P3の依頼者による試聴を別々に記録 |
| C | C5の既存catScreen条件＋動作中の顔。全世界でA+Cの同時負荷をC4の絶対予算と実機フレーム間隔で確認 |
| D：純ロジック | 移動0、上下の符号対称、累積デッドゾーン、同距離のイベント分割、Qの上限、離して450 ms以内に0、長押しとの競合、NaN/無限値を0、wheel単位換算 |

合成イベントだけではブラウザのネイティブスクロール抑止を証明できない。純関数・自動E2Eに加え、iOS SafariとAndroid Chromeで指の操作を確認する。実装後の5〜10分の試遊では「何が飛んだか分かる」「もう一度加速したい」「猫に聞こえる」「共有へ迷わず行ける」を依頼者に確かめる。未試聴・未実機の項目は合格扱いしない。改善は最大3周、同じ問題が2周残る場合は原因と残件を返す。

## 実装順と、この枠の限界

効きの大きい順は **A → D → B → C**。

1. **A：牧場1種類＋接触音から作る。** 固定tickを分け、干し草1個を確実に弾いて返す。触って芯の快感を確かめてから、6世界・高速の巻き込み・プール上限へ広げる。最初から全世界の装飾を仕上げない。
2. **D：スマホ入力とページ移動を通す。** 短い持ち替えと完走まで含めて確認する。Aが動いた状態で入力の強さと飛散の因果関係を調整する。
3. **B：3候補を合成して聴き比べる。** 依頼者が選んだ1候補だけを本番の速度連動へ入れる。試聴待ちでも、他の設計に依存しない造形作業は進められる。
4. **C：顔と耳から世界まで仕上げる。** Aの物体もCの造形方針にそろえ、全効果を出した状態で猫の収まりとスマホ負荷を最終確認する。

コード生成・外部素材なしでも、形の識別・音の母音感・衝突の快感は改善できる。一方、次の点は約束しない。

- 低コストの合成だけで実録音と区別できない猫声になる保証はない。論文の周波数へ一致しても、猫らしさは試聴で落ちることがある。
- 大都市全体の連鎖崩壊、数百の剛体同士の衝突、写実的な毛・車体の連続変形は今回の約2万三角形・追加ライブラリなしの枠では扱わない。上限内で破壊を強く見せる演出を作る。
- 実際の相対論的な衝突・ドップラー・真空の運動を同時に正しく再現する設計ではない。表示速度とscene unit、巻き込み環はゲーム上の表現。真空以降の衝撃音は鳴らさない。
- 同じ場所から始める同じ縦ジェスチャーを「加速」と「ページ移動」に意図どおり自動判別することはできない。44pxのページ移動帯という空間的な区別が必要になる。
- 三角形数・draw callの見積もりだけで全スマホ60 fpsは保証できない。実機検証と負荷削減が必要。
- この改修で増やすのは1本道の加速体験の快感であり、戦略的な深さや長期の遊び続けやすさまで得られるとはしない。依頼者の再レビューを最終判断とする。
