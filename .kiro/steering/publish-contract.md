# 公開の契約：下書きのうちに、公開したときの検査を掛ける

全アプリ横断の検査（共有・OGP・ヘッダー）は、`status: "published"` のDayにしか掛からない。
下書きのDayは、公開に切り替えたPRで初めて検査され、そこでCIに落ちる。
この穴を2つの仕組みで埋めている。単体テストで全Dayに当てる「静的な契約」（`scripts/lib/publish-contract.mjs`）と、公開の前に流す「公開ゲート」（`npm run publish:check -- --day <N>`）だ。
ここには、コードを読んでも分からない背景・理由・落とし穴だけを残す。

## Day70とDay71は、公開に切り替えたPRで横断の試験に落ちた

Day70（フリップコート）は共有欄をダイアログに置いていて、開くボタンに共通の読み上げ名「このアプリを共有する」が付いていなかった。
横断の試験はこの名前で共有欄を開くので、共有欄の表示・44pxの大きさ・URLのコピーの3件がそろって落ちた。
読み上げ名を足すと、今度は共有文から題名の副題「60秒の陣取りラリー」が抜けていることが分かった。

Day71（影証言）では、Xの共有文が正式な題名「影証言 — 灯りの高さで、証言の嘘を暴く」を含まず、共有の試験が1件落ちた。
旧い共有文は「灯りの高さで、目撃証言の嘘を暴く」で、「目撃」の2文字が余計に入っていたため、題名をそのまま含まなかった。

どちらも、下書きのあいだは横断の試験の対象外だった。公開に切り替えたPRで初めて落ち、直してからCIを流し直した。
下書きのままマージしたので本番には出ず、本人が公開を頼み直す往復も起きた。

## 静的な契約は、横断の試験が文字列だけで見ている項目の写し

6つは `tests/e2e/shared-share.spec.mjs` のテストの写しで、`build-injection` だけはビルドの差し込み方から来る。

| id | 確かめること | 写した元のテスト |
|---|---|---|
| `canonical` | 書かれていれば `https://hundred-days.pages.dev/<フォルダ名>/` と一致 | OGPとcanonical |
| `og-title` | 書かれていれば `meta.json` の題名と一致 | OGPとcanonical |
| `og-url` | 書かれていれば、ページのURLと一致 | OGPとcanonical |
| `twitter-card` | 書かれていれば `summary_large_image` | OGPとcanonical |
| `og-image` | そのDayのフォルダにあり、ビルドが配信する画像を指す。書かれていなければ `meta.json` の `screenshot` が同じ条件を満たす | OGPとcanonical |
| `share-text-title` | 共有文（`share:text`。無ければ `<title>` の `\|` より前）が、題名をそのまま含む | シェア欄（Xの投稿画面の本文） |
| `build-injection` | ビルドがタグを足すとき、足す位置（最初の `</head>`）がタグ・コメント・script などの中に入らない | （`scripts/build.mjs` の `injectAppMeta`） |

ビルドは、ソースに無いcanonical・OGPのタグを `meta.json` から足し、書いてあるタグは上書きしない。だから契約は、ソースに書かれた値だけを確かめる。
この「足す」の判定に落とし穴がある。

- ビルドがタグの有無を見るのは、`property="og:title"` のような文字列が含まれるかどうかだけだ。単引用符や大文字で書いたタグは見落とされ、もう1つ足されて二重になる。横断の試験はタグを1つに絞れないと落ちる（Playwrightの厳密な照合）ので、契約も二重を違反にした。
- 同じ文字列がコメントの中にあるだけでも、ビルドはタグを足さない。`</head>` が無いページには何も足さない。足す位置は文字列として最初の `</head>` の前なので、それがコメントの中だと、足したタグは要素にならない。
- 足す位置が属性値の中だと、足したタグの引用符で属性が途中で切れ、すでに書いてある `share:text` などの値まで変わる。検査する5種類のタグを全部書いていても、ほかのタグ（`og:description` など）が1つでも足されれば壊れるので、11個の probe の一覧を持つ `build-injection` が見る。
- ビルドは `tests/`・`tools/cache/`・`node_modules/` と、Dayごとの `tools/`・`source/` を配信しない。画像がそこにあると、手元にはあっても本番で404になる。規則は `scripts/lib/dist-files.mjs` の1か所にあり、ビルドと契約が同じものを使う。
- macOSの既定のディスクは、ファイル名の大文字・小文字を区別しない。CI（Linux）は区別するので、`og.png` を `OG.png` と書いても手元だけ通ってしまう。契約は、パスの段ごとに実際のファイル名と照合する。
- HTMLは正規表現で読むので、ブラウザの読み方とずれると、誤って合格や不合格にする。独立レビューで、文字参照（`&Amp;` は参照ではない、`&apos;` は戻す）・改行（CRLF）・属性値の中の `<meta>`・コメントの中の `</head>` のずれが見つかり、ブラウザに合わせた。
- 契約の読み取りは、適合したHTMLを前提にする。引用符のない属性値の中のアポストロフィ、`<!-->`、`<svg>` の中の `<meta>` のような非適合の書き方は、ブラウザと読み違えることがある。最終の判定は、公開ゲートのブラウザ段に任せる。

## ブラウザでしか分からない契約は、公開ゲートが受け持つ

次の5つは、計算済みのスタイル・読み上げ名・クリップボードのように、ブラウザの中でしか決まらないものが要る。

- 共有ボタンが44px以上の高さで押せること
- ボタンの枠が地色に対して3:1以上で見分けられること
- 共有欄が1つだけ据わること
- 読み上げ名で共有欄を開けること
- リンクのコピーが公開URLを渡すこと

静的に写すと、二つの実装が食い違っていくので写さない。
CSPのヘッダーも、ビルドが生成する `_headers` を見ないと確かめられないので、同じく公開ゲートに任せる。
公開ゲートは、環境変数 `PUBLISH_CHECK_DAY` でそのDayだけを公開済みとみなしてビルドし、横断の3本（`shared-share`・`external-days`・`security-headers`）をそのまま流す。

公開ゲートの作りには、次の6つの判断がある。

- `meta.json` を一時的に書き換えて試す案は捨てた。途中で止めると、作業ツリーに書き換えが残る。
- 検査用のサーバーは、公開ゲートが自分で立て、終わりに止める。Playwrightに立てさせていたときは、起動の途中で中断するとサーバーが残った。
- ポートはOSに選ばせ（`PLAYWRIGHT_PORT=0`）、サーバーの起動の1行から読む。先に空きポートを調べてから立てると、その間に別のプロセスがポートを取り、別のサーバーの200で合格しうる。
- 検査用のビルドが `dist/` に残ると、あとの通常のE2Eが下書きを含んで走る。だから、通常の終了・失敗・例外・SIGINT・SIGTERM・SIGHUP・出力先の切断では、サーバーを止めてから通常のビルドに戻す。SIGKILL や電源断のようにその場で止まると後始末は走らず、検査用のビルドが残ることがあるので、そのときは `npm run build` を実行する。
- 出力先が先に閉じる（`| head` や端末を閉じたとき）と、書き込みが EPIPE で失敗し、受け手が無いとその場で落ちて戻せなかった。出力の失敗は握りつぶし、子の出力もこちらで読んで流す。
- `PUBLISH_CHECK_DAY` は、GitHub Actions では例外にした。本番のビルドで下書きが公開される道を残さないためだ。

## 新しい違反は、見つけたPRで契約に足す

公開のときに、横断の試験が新しい種類の違反で落ちたら、同じPRで次の順に足す。

1. HTMLと `meta.json` の文字列だけで判定できるなら、`scripts/lib/publish-contract.mjs` の `CONTRACTS` に、`id`・`title`・`source`（どの横断の試験の何を写したか）・`check` の組で足す。
2. 実際に落ちた値を、失敗する例として `scripts/tests/publish-contract.test.mjs` の回帰に入れる。
3. ブラウザが要る違反なら写さない。横断の試験がまだ見ていない項目なら、横断の試験の側に足す。
4. この文書の表と、事故の節を更新する。

公開済みのDayは横断の試験を通っているので、新しい契約でも全部通るはずだ。通らないDayが出たら、まず契約の読み違いを疑う。読み違いでなければ、契約は弱めずにDayの側を直す。

## やらないこと

- CIに「下書きも含むビルド」のジョブは足さない。ワークフローの変更は本番の配信に直結し、手元で試せない。足すかどうかは、別の仕様で本人が決める。
- 横断の試験を、下書きも含めて常に流すことはしない。`dist/` は配信物なので、下書きを含めると本番に出る。
- 公開そのもの（`published` への切り替え・マージ・デプロイ・X投稿）は自動化しない。
