# 自動の引き下げの実測

2026-11-03 に tasks 4.2 の担当が測った。道具・条件は [verification-perf.md](verification-perf.md) の「測った条件」と同じ（`tools/quality-bench.mjs`、844×390・画素比2・`?touch=1`）。これはこの Mac での値で、スマホの実機の値ではない。

## 自動の引き下げ（`?touch=1&adaptive=1`、垂直同期あり、表示の準備のあとに CPU を遅くして 20 秒見る）

`Emulation.setCPUThrottlingRate` は表示の準備（`__viewReady`）のあとに掛けた（準備の時間まで遅くしないため）。降下の時刻は表示の準備（＝引き下げの見張りの開始）からの ms。始まりの段はタッチの既定の mid（1）。

測った日時 2026-11-03 20:15（JST）・負荷平均 始め 6.79 / 9.32 / 10.77 → 終わり 6.61 / 8.24 / 10.12

ほかの回（同じ道具）：
- 20:03（負荷平均 約 20。`.captures/a3-smoke/quality-bench-C.json`）：**CPU 8倍で 1→2 @7471ms、2→3 @11499ms と降下した**（コマの間隔 p50/p90 33.3/33.4ms）。遅くしない・4倍・8倍で `quality=mid` 指定・8倍で adaptive なし は降下なし
- 20:13（負荷平均 約 9。`.captures/a3-c2/`）：16倍で 1→2 @4596ms、2→3 @8615ms。遅くしない・4倍・8倍は降下なし（このときの対照は 8倍で、指定・adaptive なしとも降下なし）

読み方：
- 降下は仕様どおり：最初の段は「起動の待ち 3 秒＋窓に 1.5 秒ぶんたまる」の直後（16倍で 4.6 秒）、次の段は 4 秒あと（8.6 秒）、min（3）で止まり、上げない。`?quality=` 指定と、adaptive なし（自動操作）では、同じ遅さでも下げない
- 遅くしないとき・4倍では、コマは 60fps（16.7ms）のままで降下しない
- 8倍は境目：コマの間隔が垂直同期の2回分（33.3ms）に張り付き、判定の 34ms をわずかに下回る。機械の負荷で 34ms を超える回が混じると降下する（20:03 は降下、20:13・20:15 は降下せず）。仕様の「34ms＝約29fps を超えたら」どおりで、30fps ちょうどで回る機種では下げない
- 16倍では min まで下げても間隔は 66ms 前後のまま。CPU を遅くした重さなので、画素を減らしても軽くならない（画素数で効くのは GPU が詰まる場合）。最低の段でも重い機種では何もしない、は設計どおり
