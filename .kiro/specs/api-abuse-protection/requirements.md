# APIのBot・連打対策
公開APIの反復呼び出しによる外部サービスの負荷と利用枠の消費を抑える。Day80のゲームは静的配信のまま利用できる。

## 要件
- R1: `functions/api/` の全APIに共通の入口を設け、上流処理の前に判定する。将来のAPIにも適用する。
- R2: APIはGETだけを受ける。明示された別サイト発のブラウザ通信と8192文字を超える要求URLを、外部通信なしで拒否する。
- R3: Cloudflareが設定した接続元IPごとに、API全体で分・10秒の固定窓で60回・20回を上限とする。クエリやAPIを変えても枠を分けない。
- R4: 超過時は429のJSONとRetry-Afterを返す。拒否応答はno-storeとし、上流・後段を呼ばない。待ち時間後は再開できる。
- R5: 同じ実行環境内の同時呼び出しで上限が抜けない。状態の数・有効期間を制限し、状態保存の異常時は外部通信へ進まない。
- R6: IP・診断先URL・要求ヘッダーをログに書かない。内部Cache APIのキーにはIPのSHA-256だけを使う。X-Forwarded-Forを身元の根拠にしない。
- R6a: 別ゾーンWorkerの固定IPを正規利用者全員の枠にしない。正式中継が送るIPのハッシュをHMACで検証し、直接アクセスと同じ枠を使う。署名をメソッド・パス・クエリ・時刻に結びつけ、30秒より古い署名と署名なしWorkerを拒否する。
- R7: HTML・画像・BGM・動画・OGPと共有用クローラーに判定を掛けない。検索・通常プレイと既存APIの応答形式を維持する。
- R8: 正規の順次・並列通信、連打、異なるIP、復帰、ヘッダー偽装、保存失敗をCIで検証する。実行環境でもMiddlewareの適用を確認する。

## 運用上の境界
- ログインや書き込みフォームはなく、CAPTCHAを全画面に追加する必要はない。
- Cache APIは拠点単位で、複数の実行環境間の更新は原子的でない。これは基本的な濫用抑止であり、分散攻撃や正確な全世界の利用量管理を保証しない。
- 中継Workerや共有回線ではIPを共有することがある。元IPを外部入力のヘッダーで補完しない。正式中継の識別は署名で検証する。共有回線の利用者はなお同じ枠になる。
- Cloudflare WAFは別の設定面であり、pages.devを含む全経路の代わりにはならない。必要な権限と対象を確認する。無関係な事業サイト全体のBot設定は変更しない。
