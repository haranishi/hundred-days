# 設計：時間で割るブラウザテストの分割

## 全体の流れ
1. **測る（第1段）**：CIのブラウザテストが、Playwrightの `json` レポーターで、テストごとの所要時間を書き出し、分割ごとにartifact `e2e-timing-<n>` として保存する。書き出しは、環境変数 `E2E_TIMING_FILE` があるときだけ（手元の実行は変わらない）。
2. **記録にする**：`scripts/e2e-shards.mjs update` が、artifactのJSON（複数）を読み、テストを宣言したファイルごとの所要時間（秒）を足し上げ、`scripts/e2e-shard-durations.json` に書く。入口のspecが読み込む別のspecのテストは、入口の時間に足す（入口は `import '…spec.mjs'` の文を読んで見つける）。
3. **割る（第2段）**：`scripts/e2e-shards.mjs plan <番号>/<総数>` が、`tests/e2e/*.spec.mjs`（`testIgnore` を除く）を、記録の時間の長い順に、そのときいちばん軽い分割へ入れる（LPT法）。同じ時間は名前順で決め、結果は決定的。記録に無いファイルは、記録の中央値として入れる。番号の分割の担当ファイルだけを、1行1ファイルで出す。
4. **走らせる**：ワークフローは `mapfile -t files < <(node scripts/e2e-shards.mjs plan N/M)` で担当を受け取り、`npm run test:e2e -- "${files[@]}"` を実行する。Playwrightの位置引数は正規表現なので、出力は `tests/e2e/day-066\.spec\.mjs$` の形にする。

## 分割数
`ci-deploy.yml` の `browser` ジョブの `matrix.shard` の長さと、`env.E2E_SHARDS` の1か所に置く。第1段は、記録をとるための8分割（件数で割る従来の `--shard`）。第2段で、記録をもとに決める。

## Day080の `mounted` の確認
従来どおり、`matrix.shard == 1` で実行する（約1.6分）。割るときは、番号1の分割の初期の重さに、この時間を足す。

## 失敗の扱い
- 記録が壊れている・負の値・数値でない → `plan` は失敗する（黙って均等割りに戻さない）。
- 記録にあるが、ファイルが無い → 警告だけ（Dayの削除で落とさない）。
- 全分割に1つ以上のファイルが入らない（総数がファイル数を超える） → 失敗する。

## 検証の方針
単体テスト `scripts/tests/e2e-shards.test.mjs`：①取りこぼし・重複が無い ②同じ入力で同じ結果 ③未登録のファイルは中央値 ④偏りの上限（合成データと、コミット済みの実際の記録で、最長が合計÷分割数の1.2倍以内）⑤入口が読み込む別のspecの時間を、入口に足す ⑥壊れた記録で失敗する。
実CI：第1段のartifactで記録を作り、第2段のCIで、分割ごとの時間が揃ったかを確かめる。

## 採らなかった案
- `fullyParallel: true`：公式は勧めるが、ファイル内の実行順と1 workerの前提が崩れる。
- 分割数だけ増やす：偏りの比は変わらない。固定の準備時間（約0.5分）は小さいので、合わせて使う。
- 手元で全テストの時間を測る：CIのソフトウェア描画は、3Dの重いテストを手元の10倍以上遅くする（`swiftshader` の記録）。CIの実測を使う。
