# 2026-11-18 フォローアップ（picomatch の勧告で、全PRの依存監査が止まった件）

## 結論
修正版がどこにも無い勧告 GHSA-fc5q-39xc-vjpf が出て、`audit:deps` が全PRで失敗するようになった。待っても直らないので、この勧告だけを期限つき（2026-12-18まで）で合格にする例外を足した。critical・別の勧告・根拠のない high は、これまでどおり失敗する。

## 背景
- 勧告：GHSA-fc5q-39xc-vjpf（CVE-2026-112366・high・CVSS 7.5）。件名は「picomatch vulnerable to ReDoS through single-branch repeated extglobs」。影響は可用性だけ（`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`）。
- 範囲と修正版：picomatch `<= 4.0.7`、修正版なし。npm の最新版は 4.0.7（2026-08-24公開）。勧告が参照する上流のPR（micromatch/picomatch#194）は、2026-11-18時点で未マージで、最終更新は2026-11-09。
- 時系列：上流の公開は2026-10-19。GitHub の勧告データベースが確認して載せたのは2026-11-17 15:56 UTC。同じ日の14:59 UTC に始まった main の CI は成功していた。登録後は、変更の中身に関係なく、全PRの `audit:deps` が落ちる。
- 影響：18プロジェクト中11プロジェクト（Day56・58・59・61・64・76・79・80・82・89・92 の `source/`）。vite・vitest・fdir・tinyglobby・rollup 系の部品が picomatch を経由して high になる。

## 影響の評価
- picomatch は、全ロックの15項目（11プロジェクト）のすべてが `dev`。実行時の依存には入っていない（ロックの `dev` フラグで確認）。
- `source/` は配信されない（`scripts/lib/dist-files.mjs` の `SOURCE_DIRS_BY_APP`）。サイトの配信物は変わらない。
- ReDoS は、細工した glob を照合させたときに起きる。vite・vitest などが照合する glob は、通常、リポジトリ内の設定で決まる。各道具が glob をどこから受け取るかは、コードを読んで確かめていない。

## 決めたこと
- `overrides` で固定できる版が無いので、期限つきの例外にする。選択肢は「例外を足す」と「上流を待つ」の2つで、本人が前者を選んだ（2026-11-18）。
- 期限は30日（2026-12-18）。上流の修正PRの動きが遅いので、すぐには解けないとみた。
- 期限が来たら、修正版があれば手引きの手順で取り込み、一覧から消す。無ければ、理由を書き直して期限を延ばすかどうかを、PRで決める。
- 例外の条件は `requirements.md` の8と、`design.md` の「例外」に書いた。

## CIで見つかった別の原因（時間制限）
PR #227 の最初のCIで、17プロジェクトは例外つきで通ったが、Day79 だけ「npm auditを実行できない」で落ちた。やり直しで済ませず、原因を測った。
- Day79 の監査は、勧告が出る前のmainのCIでは約1秒、PR #226 の最初のCIでは58秒、PR #227 の最初のCIでは61秒かかった。制限の60秒に、ほぼ張りついていた。
- 手元で同じ照会を測ると、npmのcacheがあれば1.6秒。cacheを空にすると46秒で、user時間が44秒（大半がCPU）。cacheは53MB増えた。
- 原因（推定）：勧告に当たると、npm audit が、修正の候補を調べるために部品情報を大量に取りに行き、CPUで処理するとみられる。勧告が無いときは約1秒で済んでいた。Day79 は798部品で、high が16件ある。測ったのは、cacheが空のときの時間と、cacheの増え方まで。npm のコードは読んでいない。
- 直し：1回あたりの時間制限を60秒から240秒にした（`AUDIT_TIMEOUT_MS`）。CIジョブ全体の制限は15分のまま。60秒に戻ると落ちる試験を足した。
- 確認：cacheを空にして、監査全体を流し直した。18プロジェクトで失敗0件、合計63秒（Day79 は約46秒）。

## 確認していないこと

- 各道具が picomatch に渡す glob の出どころ。
- PR の CI の結果（PR の画面が正）。

## 例外を外す手順
1. 修正版が出たら、`.kiro/steering/dependency-updates.md` の手順で、いちばん古い修正版へ上げる（`--before` で公開から3日以上の版を選ぶ）。
2. `AUDIT_EXCEPTIONS` から該当の項目を消し、`npm run audit:deps` が例外なしで通ることを確かめる。
3. 期限が切れたのに修正版が無いときは、項目の `expires` と `reason` を書き直す。延ばす理由は、このフォルダのフォローアップに残す。
