# Day 016「回線の犯人さがし」

速度を測るアプリではなく、**その遅さの原因が家の中にあるのか外にあるのかを判定する**アプリ。

## なぜ作ったか

「Wi-Fiが遅い」と感じた人が最初にやるのは速度テストだが、出てくるのは数字だけで、次に何をすればいいのか分からない。結果、効かないルーター買い替えに金を使う。

実際に自宅の回線を4日間・73回測って切り分けたとき、役に立ったのは瞬間の数字ではなく次の3つだった。ここだけを誰でも使える形にした。

- **上りと下りの非対称** — 上りが出ているのに下りだけ遅いなら、同じ電波・同じ線を通っている以上、宅内の機器は犯人になれない
- **通信中に遅延が跳ねるか** — 速度が出ていても通話やゲームが途切れる原因。普通の速度テストには出てこない
- **時間帯でどう変わるか** — 単発では絶対に分からない。同じ夜でも数値は何倍も振れる

## 設計上の判断

**測定エンジンを自前で書いた。** `@cloudflare/speedtest` は高機能だが、測定結果を完了時に提供元へ送信する。このアプリは画面に「どこにも送信しません」と書くので、実装がその記述と食い違ってはいけない。npm依存もバンドラも持たないリポジトリの構成にも合う。

**IPアドレスを使わない。** 測定先の応答ヘッダにはIP・都市名・郵便番号・緯度経度が入っている。IPv6接続かどうかの判定にだけ使い、値はその場で捨てる。保存も表示も共有もしない。

**1回では結論を出さない。** 履歴が3件未満のあいだは時間帯の判定を出さず、「1回では判断できません」と表示する。回線速度は同じ日でも大きく振れるので、単発で断定するのが一番やってはいけないことだった。

**確認をブラウザのダイアログでやらない。** 履歴の全消しは同じボタンを2回押す方式。ダイアログは測定中に出ると通信を止めるうえ、自動テストからも扱いにくい。

## 指標の目安をどう決めたか

数字を出すだけでは「で、これはいいの？」に答えられない。かといって点数だけ付けると、価値判断を押しつけることになる。そこで**どの帯にも「その速さで何ができるか」を必ず添え、A+〜Fは要約として扱う**。

しきい値は感覚ではなく、**実際の用途が要求する値**から引いた。下りはNetflixの推奨速度（フルHD=5Mbps・4K=25Mbps）、上りはZoomの1080p送信（3.0Mbps）、遅延はITU-T G.114とゲームのping、ゆらぎは通話が崩れ始める30ms。出典はアプリの目安表の中にリンクで置いてある。

⚠️ **遅延は往復時間で測っている。** G.114が定めるのは片道なので、片道150ms＝往復300msとして換算した値をFの入口に置いた。

しきい値の定義は `lib/scales.js` の1か所だけにある。画面の目安表も、各数値のバッジも、通信中の反応の採点も、すべてそこから引いている。

## ブラウザにできないこと（要件から外した）

- **Wi-Fiの電波強度・チャンネル・リンク速度** — OSのAPIでしか取れない。だからここで測れるのは「Wi-Fi区間＋回線の合計」であって、Wi-Fi単体ではない
- **IPv4とIPv6の測り分け** — 接続先のIPバージョンをブラウザから指定できない
- **定期的な自動測定** — タブを閉じたら動かない。代わりに測るたび履歴を貯める
- **パケットロス** — WebRTCのTURNサーバーを自前で運用する必要があり、無料で完結しない

## 構成

- `lib/measure.js` — 測定。ネットワークに触るのはここだけ。fetchと時計を差し替えられるのでテストから駆動できる
- `lib/diagnose.js` — 判定。純粋関数のみ。診断8分岐は全部ユニットテストがある
- `lib/history.js` — localStorageの読み書き。壊れたデータを黙って捨てず、消すかどうかは利用者に決めさせる
- `app.js` — 状態の出し分けと描画だけ

```bash
npm run test:unit    # 44本（判定・保存・段取り）
npm run test:e2e     # 4状態と診断の表示
```
