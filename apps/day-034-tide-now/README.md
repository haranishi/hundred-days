# Day 034「潮、いまどっち？」

## 何をするか

**いまの潮は満ちているのか、引いているのか。** 地点を選ぶと、気象庁の潮位表から1行で答えます。次の満潮・干潮は「時刻と潮位」を1行、「あと何分か」をその下に大きく分けて出し、いまの潮位の推定、潮名、きょうの干満差を添え、きょうのカーブと、きょう・あすの満干の表を表示します。

## なぜ作ったか

釣り・潮干狩り・磯遊び・海辺の散歩で知りたい「いま」と「次の干満」を、月間の表から探す手間を減らすためです。地点を決めたら見出しとカーブで答えることを、要件定義の中心に置いています。

## 答えの出し方

潮位表テキストの1行136文字を、24個の毎時潮位・日付・地点記号・満潮と干潮に分けます。時刻は時と分それぞれの空白詰めを読み、該当なしの値は満干として数えません。高さの単位はcmで、潮位表基準面からの値です。

日本時間のきのう・きょう・あすの満干を絶対時刻で並べ、いま以前の最後と、いまより後の最初を探します。満干の前後30分以内（30分ちょうども含む）は「満潮のころ」「干潮のころ」。それ以外は次の満干、次が無ければ前の満干から「いま、満ち潮」「いま、引き潮」を出します。両方なければ向きが分からないと表示します。

いまの高さは前後の満干の余弦補間です。片方が欠ければ毎時値の線形補間に切り替え、23時台は取得済みのあす0時も使います。補間に使う先の値がない端では最後の毎時値を使います。画面には「およそ」「推定」を添えます。カーブは毎時値と満干点を通る単調三次補間で、あす0時が取得できれば24時まで描きます。取得できなければ最後の公表値まで描き、未知の24時の値は作りません。

干満差は満潮の最大値から干潮の最小値を引き、片方の満干がなければその側を毎時値の最大・最小で補います。その年の干満差の分布で、下位1/3を「小さい方」、上位1/3を「大きい方」、間を「ふつう」と表示します。同値は中間順位に置きます。

潮名はDay 026からファイルごと複製した `lib/astro.js` で月と太陽の黄経を求め、その差を0〜360°にそろえて分類します。要件定義にある黄経差方式（[Wikipedia「潮汐」](https://ja.wikipedia.org/wiki/潮汐)の黄経差を用いた方式）に従い、大潮は348〜36°および168〜216°、ほかは要件定義の中潮・小潮・長潮・若潮の区分です。各区間は下限を含み、上限を含みません。新聞・雑誌などの旧暦方式とは1日ずれうるため、画面にも「黄経差から」と方式を添えます。

固定時計2026年9月10日15:00 JSTの計算結果は黄経差348.5054927778626°で大潮です。東京の次の満潮は16:57・201cm、干満差171cm（大きい方）、いまの推定は165.2489…cmで「およそ165cm」と表示します。

## 設計上の判断

- 地点がないあいだは潮位表も地点一覧も読みません。地点一覧は選択・現在地・保存地点の復元時にだけ読みます。
- 外部通信は気象庁の潮位表テキストだけです。年ごとのファイルを取得し、必要な3日が年をまたぐ場合だけ隣年も取得します。同じ地点・年の成功した取得は、画面が開いている間メモリで共有します。失敗した取得だけは手動で再試行できます。
- 隣年が取得できなくても当年で答えを出します。1分ごとの更新は手元のデータを再計算するだけで、通信しません。翌年まで開き続けて必要な日が手元になければ、きょうの表が見つからない状態になります。
- 現在地は端末の中で239地点と照合し、最寄りまでの距離を四捨五入して表示します。50km以上なら参考程度にという但し書きを出します。
- 保存するのは地点コードと選び方だけです。座標・距離・潮位表は保存しません。現在地モードで再訪したときは地点を復元し、距離は「距離は現在地で再確認」と表示します。「現在地」を押すと再計算できます。
- エラーは地点名を入れた文言と、次にできることを対にします。404は「別の地点を選んでください」、通信失敗は「通信を確かめて、もう一度読んでください」、形の変化は「気象庁の配信が変わった可能性があります」。取得層は画面の文言を持たず、応答の番号（`error.status`）だけを渡します。
- カーブの縦軸は、その日の値に合わせて10・20・50・100cm（干満差の大きい地点は200・500cm）から刻みを選び、その倍数で3〜5本引きます。東京の日は0・100・200、干満差27cmの秋田の日は10・20・30・40です。目盛りの間隔をそろえることより、読んだ数字がきりのよい値であることを優先しています。単位は軸の脇に置かず、いちばん上の目盛りにだけ付けます（「200cm」）。満潮の時刻は点の上、干潮の時刻は常に点の下に書き、そのぶん下端を上げて時刻の軸と離しました。上下が点ごとに入れ替わると、どちらの点の時刻なのかを読み取り直すことになるためです。
- ボタンの強さは塗り・アウトライン・リンク風の3段階しか使わず、いま押してほしいものだけを塗りにします。地点がないときは「現在地でいまの潮を見る」、潮位表が取れなかったときは「地点を変える」、地点を選ぶダイアログでは「この地点にする」が塗りです。同じボタンでも画面によって強さが変わるのは、次にすることが画面ごとに違うからです。
- 満干の無い側は表に「予測なし」と書き、エラーや地点未選択でも出典と推算値の注意書きを常設します。
- 「現在地の座標は端末の外に出しません」は、現在地を押しうる画面（地点がないとき・現在地で見ているとき）にだけ出します。自分で地点を選んだ人には関係のない断り書きだからです。

## 出典と規約

出典：[気象庁ホームページ 潮位表](https://www.data.jma.go.jp/kaiyou/db/tide/suisan/index.php)を加工して作成。

[気象庁ホームページ利用規約](https://www.jma.go.jp/jma/kishou/info/coment.html)と[公共データ利用規約（第1.0版）](https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/f7fde41d-ffca-4b2a-9b25-94b8a701a037/24afdf33/20240705_resources_data_outline_05.pdf)に従い、出典と加工したことを画面にも明記しています。

取得先は `https://www.data.jma.go.jp/kaiyou/data/db/tide/suisan/txt/{YYYY}/{CODE}.txt` です。認証なしでブラウザから取得します。

同梱の地点データは[潮位表掲載地点一覧表](https://www.data.jma.go.jp/kaiyou/db/tide/suisan/station.php)の239地点です。用意済みの `tools/build-stations.mjs` が緯度経度・地点記号・平均海面などを読み、Day 033の市区町村代表点で最寄りの都道府県を付けた39都道府県のデータをそのまま使っています。南鳥島は東京都。内陸8県には地点がなく、県境付近の分類はこの近似に基づきます。座標は分単位で、厳密な海岸線や現在地の潮位を表すものではありません。基準面の注記とMSLは同梱データに保持し、MSLへの高さ換算はしていません。

市区町村代表点の元データは[令和2年国勢調査（総務省統計局）](https://www.stat.go.jp/data/kokusei/2020/)と[e-Stat統計GIS](https://www.e-stat.go.jp/gis)です。天文計算はリポジトリ内の自作コード、時刻・保存・距離計算はDay 033を踏襲しています。外部ライブラリ・画像・フォント・音源は追加していません。

## 制約

**推算値であり実測ではありません。** 気象庁の天文潮の推算値を加工したもので、実際の潮位は気圧・風・波によって変わります。海の安全にかかわる判断は公式の情報で確認してください。高潮・津波の情報、潮流、天気、釣果、月間表は扱いません。

取得は8秒で中断します。当年の404・通信失敗・形の変化はエラー、きょうの行がなければemptyです。公表範囲外の満干は作りません。端末のタイムゾーンにかかわらず日付・時刻はAsia/Tokyoを使います。

ユニットは `node --test apps/day-034-tide-now/tests/` と `TZ=UTC node --test apps/day-034-tide-now/tests/`。E2Eは `tests/e2e/day-034-tide-now.spec.mjs` です。E2Eとデモは同梱の実物の固定データへ通信を差し替えます。E2E時だけmeta.jsonのstatusを一時的にpublishedとしてbuildし、終了後は必ずdraftへ戻します。

`demo-scenario.mjs` は2026年9月10日15:00 JSTの東京を再現する約17秒の操作と、1200×750のスクショ設定をexportします。file://からは同じフォルダのミニHTTPサーバーへ開き直します。撮影後は映像を見て、見出しが現れる途中を先頭にする切り位置を `tools/trim-demo.mjs` へ渡します。映像（18秒・1コマ目は見出しが現れる途中）・スクショ・36秒のプロモ動画（`tools/promo/`・-16.8 LUFS）は本体側で生成し、目視で確認しています。

検証結果（2026-09-10）：ユニット59件は通常環境・`TZ=UTC` の両方で成功。E2Eは Day 034 の26件と共通の shared-share・security-headers を合わせた162件が成功。`npm run build` と `npm run precheck` も通過しています。スクリーンショット採点（別セッションのAIが10項目・20点満点でゼロベース採点）は3周で 12→14→13 点。合格の16点には届かず、残った指摘（PC幅で答えの右側が空く・取得中の高さ確保・グラフの干潮ラベルと0の線の近さなど）は次回の改修候補として作業記録に残しています。
