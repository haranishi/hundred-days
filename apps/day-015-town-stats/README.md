# Day 015「あなたの街のステータス」

https://hundred-days.pages.dev/day-015-town-stats/

市区町村を選ぶと、その街の人口・年齢・世帯のかたちを**ステータスカード**にして表示します。
全国1,741市区町村の中での順位と、全国中央値との比べ棒つき。2つの街を並べて眺められます。

## 数字はぜんぶ国の統計

- 人口・年齢・世帯: **令和2年国勢調査**（総務省統計局・2020年10月1日時点）
- 面積: **全国都道府県市区町村別面積調**（国土地理院・令和8年4月1日時点）
- ひとり暮らし世帯の割合だけは、一般世帯数から独自に割り算した（＝加工。その旨を画面にも明記）
- 人口密度は国勢調査の公式値をそのまま使う。**2026年の面積と2020年の人口を混ぜて再計算しない**
  （新しく見える数字を作るより、出どころのはっきりした数字を出す）

## 「ランキングアプリ」にしなかった理由

もとの題材は「地域ランキング」。でも順位で街を序列化する見せ方は、
規約より先に人を傷つける。そこで**設計で決めたこと**：

- **良い/悪いを言わない。** 順位は「多い方から◯位」と方向を事実として言うだけ
- **合成スコア・偏差値・総合ランキングを作らない**（「住みやすさ◯位」は統計ではなく編集）
- **属性の序列化につながる指標は最初から扱わない**（意図的な除外）
- 逆順の一覧を「ワースト」と呼ばない。そもそも一覧ページを作らず、街は1つずつ見る
- この方針はE2Eテストで固定してある（価値判断語が画面に出たらテストが落ちる）

規約面も着手前に一次情報で確認した：e-Statの利用規約はCC BY 4.0互換で商用利用可、
数値データ自体はそもそも著作権の対象外。国土地理院はPDL1.0で出典明示のみ。
どちらも「出典＋加工した旨」を画面に常設している。

## 順位と中央値の扱い

- 母数は**1,741市区町村**（政令指定都市は市単位・東京は特別区単位）。政令市の区は収録しない
- 同値は競技方式（1, 2, 2, 4位）。値が無い街は順位も母数からも外す
- 比べ棒は全国**中央値**を50%の位置に置く。平均だと大都市に引っ張られて
  ほとんどの街が「下」に見えてしまう
- 2020年の双葉町は全町避難で、元の表でも人口が「-」。0に書き換えず「—」のまま出す。
  帰還が始まったばかりの自治体では増減率などに極端な値がそのまま出る。
  これも一覧やランキングにはせず、その街を選んだ人にだけ、調査時点つきで見せる

## ローカルLLM実験の日

この日は実装をクラウドのAIではなく、**この手元のMacで動くGemma 3 27B**（Ollama）に
下書きさせる実験をした。仕様書を渡して生成させ、人間（別のAI）が検収して差し戻すループ。
結果の記録：

- データ変換ツール（xlsxのZIPを自前で解く処理）: **2周とも不合格**。1周目は検収で13件の指摘、
  2周目は指摘を渡したのに存在しないAPIや別のタグ名を作話して悪化した。
  ルール（同じ失敗2回で人に返す）に従い、このファイルだけ検収側が書いた
- 生成速度は約12トークン/秒。1ファイルあたり5〜8分
- 受け入れテスト（ユニット・E2E）は検収側が先に書き、生成物がそれに合格するまで回した

## 動かし方

データを作り直すときだけ（アプリは同梱JSONを読むのでビルド不要）：

```bash
# tools/cache/ に2つの元ファイルを置いてから
node tools/build-data.mjs
```

元ファイルの入手先はどちらも公式サイト：
[e-Stat 令和2年国勢調査「都道府県・市区町村別の主な結果」](https://www.e-stat.go.jp/stat-search/files?stat_infid=000032143614)／
[国土地理院 面積調CSV](https://www.gsi.go.jp/KOKUJYOHO/OLD-MENCHO-title.htm)

「令和2年国勢調査」（総務省統計局）および「全国都道府県市区町村別面積調」（国土地理院）を加工して作成。
本アプリは国の公式サービスではなく、数値の正確性は保証されません。
