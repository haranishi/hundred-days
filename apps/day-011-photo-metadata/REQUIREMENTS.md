# Day 011 要件定義：この写真、まだ場所を覚えている

設計の根拠は [DESIGN.md](DESIGN.md)（ユーザーストーリー＋UX5階層）。ここには「作るもの」だけを書く。

## 目的

写真をSNSやフリマに出す前に、その写真が抱えている位置情報・個人につながる情報を10秒で確かめ、消して保存できるようにする。**写真は一切どこにも送らない。**

## 主要アクション（1本）

JPEGを置く → 入っているものが危険度順に出る → 消して保存する。

## この日の範囲（Day 11–20 の解禁）

- 解禁されたのは **③UIの状態＝4状態対応（空・読込中・エラー・不正入力）**。この4つを飾りでなく必然として使う
- **localStorage は使わない**（Day 21解禁）
- **外部APIは使わない**（Day 31解禁）。通信を1本も出さないことをE2Eで固定する
- 地図タイルも外部依存なので出さない。座標は数値で表示する

## 対応する形式

| 形式 | 挙動 |
|---|---|
| JPEG（先頭が `FF D8 FF`） | 解析・除去の両方に対応 |
| それ以外（PNG / HEIC / WebP / 画像でないファイル） | **「調べられません」と明示する。「情報はありません」とは絶対に言わない**（安全だと誤解させるため） |

判定は拡張子ではなく**先頭バイト**で行う。`.jpg` に改名されたHEICを取り違えない。

## 画面の状態（`<main data-state="...">` で切り替える）

| 状態 | 出るとき | 出すもの |
|---|---|---|
| `empty` | 初期表示・「別の写真を試す」後 | ドロップゾーン・使い方1行・サンプルを試すボタン・送信しない旨 |
| `loading` | ファイルを受け取ってから解析が終わるまで（**必ず1回経由する**） | 進行中の表示。ただし文字の表示は120ms以上かかったときだけ（一瞬で終わるのに偽の待ち時間を作らない） |
| `result` | JPEGの解析に成功 | 危険度順の結果・除去ボタン。Exifが無い場合も `result` の一種として「見つかりませんでした」を出す |
| `unsupported` | JPEGでない | 「このツールでは調べられません」＋対応形式の説明 |
| `error` | JPEGとして最後まで読めない（区切りが壊れている） | 何が起きたか・別の写真を試す導線 |

> ⚠️ 当初この表は「Exifの構造が壊れている」も `error` に入れていたが、**それでは区画を消せないまま行き止まりになる**（区画の除去はExifの解析結果に依存しない）。実装では「Exifが読めないだけ」は `result` 側で扱い、保存ボタンを出す。
| `invalid` | 0バイト / 50MB超 / 複数ファイル同時 | 何がだめだったかを具体的に言う |

状態の遷移は `<main>` の `data-state-log`（カンマ区切り）に追記する。E2Eで `loading` を経由したことを検証するため。

## 解析して出すもの（危険度の3段。色だけでなく必ず文字ラベルを付ける）

### 1. 場所

`GPSLatitude` / `GPSLongitude`（度分秒→十進に変換）・`GPSAltitude`・`GPSDateStamp` / `GPSTimeStamp`・`GPSImgDirection`。
緯度経度は十進6桁で表示し、「この座標を検索すれば場所が分かる」ことを一行添える。**住所には変換しない**（外部API不要・リスク増）。

### 2. あなたにつながるもの

`CameraOwnerName`(0xA430) / `BodySerialNumber`(0xA431) / `LensSerialNumber`(0xA435) / `Artist`(0x013B) / `Copyright`(0x8298) / `UserComment`(0x9286) / `ImageDescription`(0x010E) / `XPTitle`(0x9C9B) / `XPComment`(0x9C9C) / `XPAuthor`(0x9C9D) / `XPKeywords`(0x9C9E) / `MakerNote`(0x927C＝中身は読まず「メーカー独自の記録あり」とだけ) / **埋め込みサムネイル（IFD1）**。

シリアル番号が出たときは「**同じカメラで撮った他の写真と結びつけられます**」を添える。ここがこのアプリの見せ場。

### 3. 撮影の設定

`Make` / `Model` / `Software` / `DateTimeOriginal` / `Orientation` / `ExposureTime` / `FNumber` / `ISO` / `FocalLength` / `LensModel`。初期状態は畳んでおく。

上のどれにも当てはまらないタグは、中身を出さず「ほかに◯件」と件数だけ出す。

### 埋め込みサムネイル

IFD1 の `JPEGInterchangeFormat` / `JPEGInterchangeFormatLength` から切り出し、blob URL で画面に出す。
文言は**断定しない**：「編集する前の見た目が残っていることが**あります**。本体の写真と見比べてください」。本体との自動比較はしない（1日の枠を超える）。

## 消し方（差別化の核・ここを間違えると価値が消える）

**画像を描き直さない。** canvas で再エンコードすると画質が落ちる。JPEGのセグメント構造を直接編集して、メタデータの区画だけを取り除き、圧縮された画素のデータ（SOS以降）は1バイトも変えずにコピーする。

| セグメント | 扱い | 理由 |
|---|---|---|
| APP1 `Exif\0\0` | **消す** | 本体 |
| APP1 XMP (`http://ns.adobe.com/xap/1.0/`) | **消す** | GPS・作者情報が入りうる |
| APP13 Photoshop/IPTC | **消す** | 作者・連絡先が入りうる |
| APP2 MPF | **消す** | 別の画像を抱えていることがある |
| COM（コメント） | **消す** | 任意の文字列 |
| APP2 `ICC_PROFILE` | **残す** | 色の再現に使う。個人には結びつかない。消すと色が変わる実害の方が大きい |
| APP0 JFIF / APP14 Adobe | **残す** | 復号に関わる |

**向きだけは作り直して残す。** Exifを丸ごと消すと、`Orientation` が 1 以外の縦写真がブラウザで横倒しに表示される。元の `Orientation` が 1 以外だったときに限り、**`Orientation` 1エントリだけの最小のExif**（"Exif\0\0" + TIFFヘッダ + IFD0 1件 + 次IFDなし）を作って差し込む。
画面には「向きの情報だけ残しています」と書き、**それも消すチェックボックス**を1つ置く（既定はオフ＝残す）。

## 確かめられること（信頼の担保）

- 空状態と結果状態の**両方**に「この写真はあなたのブラウザの中だけで処理され、どこにも送られていません」を出す
- 保存したあと、その写真をもう一度ここに置いて確かめる導線を出す
- E2Eで**同一オリジン以外への通信が0本**であることを検証する

# 調査で確定した事実と、そこから足す要件（2026-08-18 追記）

> ⚠️ **以下の追記1〜4は、法律家のレビューを受けていない自己調査のメモである。** 条文・ガイドライン・判例の一次情報にあたって書いてはいるが、法的助言ではない。ここでの整理を根拠に他者へ助言しないこと。

以下は一次情報（CIPA Exif 2.32規格・Adobe XMP仕様・W3C PNG仕様・WHATWG HTML仕様・個人情報保護委員会ガイドライン）と、日本語Exif削除ツール7件の実地調査にもとづく。**推測ではなく確認済みの事実だけを書いている。**

## A. 差別化はここにある（競合7件を実際に読んだ結果）

日本語のExif削除Webツール7件（プチモンテ／こませ／アサリツールズ／やまどり／FreeTool／Crecel／ITKAGYO）を調べたところ、**次の3点を書いているサービスは1件もなかった**。

| 誰も書いていないこと | このアプリはどうするか |
|---|---|
| メタデータの**完全な除去を保証しない**こと | 免責として明記する |
| **Exifを消してもXMP・IPTCに同じ著作権/撮影者情報が残る**こと | 3つとも消す。そのうえで画面に書く |
| 他人の写真の**権利表示を消すことのリスク** | `Copyright`／`Artist` を検出したら消す前に警告する |

「ブラウザ内で完結・サーバーに送信しない」は7件全部が書いており、**それ自体は差別化にならない**。差別化は上の3点と、無劣化（再エンコードしない）である。

## B. 実装の落とし穴（規格を読んで判明。ここを外すと機能が嘘になる）

1. **APP1は2種類ある。** `Exif\0\0` で始まるものと `http://ns.adobe.com/xap/1.0/\0`（XMP）で始まるものが両方APP1。**「最初のAPP1を消す」実装は必ずXMPを取り逃す**。マーカー番号ではなく**シグネチャ文字列で判別**すること
2. **同じ種類のセグメントが複数あることがある。** Exif APP1もPSIR APP13も64KBを超えると複数ブロックに分割される。XMPも64KB超で ExtendedXMP として複数APP1にまたがる。**一致するものを全部消す。最初の1つで打ち切らない**
3. **canvas再エンコードを選ばない理由（裏が取れた）**：WHATWG HTML仕様上、`canvas.toBlob()` の出力に含まれるのは「ビットマップの画素」「96dpi固定の解像度」「**canvasの色空間を示す**カラープロファイル」だけ。元ファイルのICCは引き継がれず、Adobe RGBやDisplay P3の写真は**sRGBに焼き込まれて戻らない**。JPEGは必ず再圧縮され、元の量子化テーブルも失われる
4. **向きの問題は実在する。** CSS `image-orientation` の初期値は `from-image`＝ブラウザは既定でExifのOrientationを適用する。**Exifを丸ごと消すと、正しく表示されていた縦写真が横倒しになる**。7件中2件（プチモンテ・やまどり）だけがこれに対処している
5. **PNGにも `eXIf` チャンクがあり得る**（W3C PNG仕様 §11.3.4.5）。「PNGだからEXIFは無い」と決めつけない。このアプリはPNGを**「調べられません」**と返すので誤答にはならないが、「情報はありません」と言ってはいけない理由がここにある
6. **ICCプロファイルはAPP2 `ICC_PROFILE\0`。** 消すと色が変わる。**残す**（既に上で決定済み）
7. **MakerNoteは中身を読まない。** メーカー独自形式で規格上フォーマット非公開。存在の有無だけ出す

## C. 画面に必ず書く事実（他社が書いていない＝ここが価値）

- 「Exifを消しても、**XMPやIPTCという別の場所に同じ撮影者名・著作権表示が入っていることがあります**。このアプリは3つとも消します」
- 「**完全に消せることを保証するものではありません**」（下記Dのとおり、断定を避ける）
- 「写真に**写り込んだ表札やナンバープレートは、メタデータを消しても消えません**」

## D. 個人情報保護法の調査結果から来る実装条件

調査の結論：**この設計（完全クライアントサイド・一切送信しない）なら、運営者に個人情報保護法17条・18条・20条・21条・23条の義務は生じない。** 理由は義務の免除ではなく、**義務の発生要件である「取得」「取扱い」が技術的に発生していない**ため。個人情報保護委員会の通則編3-3-1注※1は「単に閲覧するにすぎず、転記等を行わない場合は、個人情報を取得しているとは解されない」としており、本件は閲覧すらしていない。

この立場は強いが、**送信経路を1本足した瞬間に崩れる**。したがって次を実装条件とする。

1. **画像由来のデータを、どんな形でも外に出さない。** 座標・ハッシュ値・「GPSの有無」フラグ・ファイル名すら送らない
2. **エラーログにExifの値やファイル名を混ぜない。** 例外オブジェクトに混入したものを将来外部送信すると、意図せず「取得」が成立し得る
3. **このアプリを `scripts/build.mjs` の `CONNECT_BY_APP` に足さない。** `connect-src 'self'` のままにすることが、そのまま「送信できない」ことの技術的保証になる
4. **E2Eの「送信ゼロ」テストは、機能テストであると同時に法的主張の証拠である。** 必ず入れる
5. **このアプリのページにアクセス解析タグを入れない**（同一ページに解析タグがあると「送信していない」という説明の信頼性が落ちる）

## E. 画面に書く文言のルール

- **事実を書く。法的評価を書かない。** 「画像はサーバーに送信されません」（事実）は書く。「個人情報保護法上の義務はありません」（評価）は書かない
- 「オフラインでも動きます」は**検証可能な主張**なので書いてよい（実際に動くことを確認してから）
- 免責は「一切の責任を負いません」という全部免責の書き方をしない。**何を保証しないかを具体的に書く**

# 追記2：責任・免責の調査から来る要件（2026-08-18・実装後に反映する分を含む）

## F. 分かったこと（一次情報で確認済み）

1. **PL法は適用されない。** 製造物責任法2条1項の「製造物」は「製造又は加工された動産」で、消費者庁の公式Q&A（Q3・Q5）が**ソフトウェアは対象外**と明言している。したがって責任論は民法709条一本
2. **無償でも709条の責任は成立しうる。** 「無償だから注意義務が下がる」という一般規定は現行民法に無い（法制審で無償役務提供者の注意義務軽減規定が提案されたが、2017年改正で**採用されなかった**）。消費者庁のPL法Q&A Q15も「無償であることのみを理由に対象から除外されるとは解されない」としている
3. **「一切の責任を負いません」は書いても意味がない。** 消費者庁の逐条解説が、全部免責条項を消費者契約法8条1項1号・3号で**無効となる事例**として明示している（事例8-1〜8-3）。しかも無効になったからといって責任が増えるわけではなく、**単にリスク低減の役に立たないだけ**
4. **有効な書き方は2つ。** ①**何を保証しないかを具体的に列挙する** ②責任制限は「**当方に軽過失がある場合に限り**」と明記する（消費者契約法8条3項。逐条解説はこの書き方を有効例として挙げ、逆に「法律上許される限り」は**無効**としている）
5. **電気通信事業法の外部送信規律（27条の12）は対象外と読める。** 総務省の参入マニュアル・ガイドブック・パンフレット・FAQがそろって「個人や企業等の専ら**自己の情報発信のためのホームページの開設**」を自己需要＝電気通信事業に該当しないと整理している。ただしこのアプリのページに解析タグを入れない方針なので、そもそも論点にならない

## G. 免責の文言より、画面と実装のほうが効く（最重要）

契約が成立しているか怪しい（ログイン不要・同意画面なし）ので、**免責条項は契約条項として拘束力を持たない可能性がある**。一方、画面上の説明は契約が無くても709条の過失判断に効く。したがって**文言より実装に投資する**。

### G-1. 追加する機能：書き出したファイルの自動再検証（必須）

保存する直前（またはダウンロード完了時）に、**このツール自身が書き出し後のバイト列をもう一度解析して、「何が残っているか」を画面に出す。**

- 「Exif・XMP・IPTC・コメント：**なし**」「ICCプロファイル：**残しています（色のため）**」「向きの情報：**残しています**」のように、除去後の状態を項目ごとに示す
- 設計文書（DESIGN.md ③構造）にあった「保存した写真をもう一度置いて確かめる導線」を**手動から自動へ格上げ**する。手動導線も残してよい
- これは信頼の担保であると同時に、**「利用者が結果を検証できる状態を提供した」という事実**になる

### G-2. 「保証しないこと」を、ページの奥ではなく結果表示のすぐ近くに置く

利用規約ページの奥に隠さない。**結果が出ている画面の中**に、次の3点を読める形で置く。

- **すべてのメタデータを完全に取り除けることは保証していない**（XMP・IPTC・ICC・MakerNote・埋め込みサムネイルなど、形式や機材によっては検出・除去できない領域が残ることがある）
- **「見つかりませんでした」は「情報が入っていない」という意味ではない**
- **未対応の形式に出る「調べられません」は、そのファイルが安全という意味ではない**

### G-3. 免責文言の書き方（`lib/copy.js`）

- 「一切の責任を負いません」と**書かない**
- 責任制限を書くなら「**当方に軽過失（故意および重大な過失を除く過失）がある場合に限り**」と明記する
- 生命・身体の侵害を対象に含める書き方をしない（軽過失でも消費者契約法10条で無効になり得るため）
- **法的評価を書かない**（§E再掲）

### G-4. 既知の制約を、バージョンつきでファイルに残す

`README.md` に「対応している形式」「検出できる領域」「**検出できない領域**」を明記し、更新したら日付を残す。義務の水準は「その当時の客観的情報」で画されるという裁判例（東京地判平成26年1月23日）があるため、**その時点で知られていた制約に対応していた証跡**になる。

### G-5. 不具合の報告先を出す

画面から GitHub のリポジトリに到達できるようにする（共通シェアとは別に、フッターへ1行）。指摘を受けてから遅滞なく直す運用にすること自体が、責任判断で有利に働く（東京地判平成14年4月22日）。

# 追記3：著作権法（権利管理情報）から来る要件（2026-08-18）

## H. 条文の確定

- **みなし侵害＝著作権法113条8項2号**「権利管理情報を故意に除去し、又は改変する行為（…やむを得ないと認められる場合を除く。）」
- **定義＝著作権法2条1項22号**
- ⚠️ ネット上の解説の多くが「113条3項」と書いているが、**2018年・2020年・2021年の3度の挿入で移動しており誤り**。孫引きしないこと

## I. 定義の3要件と、Exifタグの評価

権利管理情報の定義は3要件。①イ〜ハのいずれかに該当（イ＝著作物や権利者を特定する情報／ロ＝利用許諾の方法・条件／ハ＝照合により特定できる情報）②電磁的方法で著作物と一体に記録・送信される③**電子計算機による著作権等の管理に現に用いられている**（用いられていないものは除外）。

**争点は③にある。** カメラが設定値を自動で書き込んだだけの `Artist` は、通常どの権利管理システムにも接続されていない。「単なる著作者名の記載」は①は通るが③で落ちうる。

ただし**③を満たすかはファイルの中身から判定できない**（外部システムで使われているかの問題のため）。したがってアプリは**「当たりうる前提」で設計する**。

なお、**画像に焼き込まれた目視可能な©クレジットは「電磁的方法」に当たらず、権利管理情報ではない**（人の知覚で認識できないものに限る定義のため）。直感に反するが条文上こうなっている。

## J. 提供者の責任：条文の不存在がいちばん強い論拠

技術的保護手段については**120条の2第1号が回避ツールの提供そのものを処罰する**のに対し、**権利管理情報にはこの種の道具提供罪が存在しない**。120条の2第5号が処罰するのは除去した本人で、しかも**営利目的の場合に限る**（かつ親告罪）。米国も同じ構造（DMCA §1201にtrafficking規定があり、§1202には無い）。

判例側も本件に有利：ロクラクII最判は「単に複製を容易にするための環境等を整備しているにとどまらず」枢要な行為をした者を主体とする＝**環境整備にとどまる者は主体でない**。音楽教室最判は「**提供者の行為を要することなく利用者の行為のみにより成り立つ**」類型で主体性を否定。文化審議会の公式資料も「**コピー機のような一般品の提供…を理由に差止請求の相手方とするのは不適切**」と明言している。

## K. v1で実装すること

1. **`Copyright`(0x8298) と `Artist`(0x013B) を「あなたにつながるもの」から切り離し、第4のカテゴリ「権利表示」を作る。**
   理由：**利用者の利益の向きが逆**だから。GPSは消したい情報だが、著作権表示は残したい情報。同じ束に入れると「全部消す」が正解に見えてしまう
2. **XMP・IPTCの区画があるときも、権利表示が入っている可能性を示す。** XMPはテキストなので `dc:rights` / `dc:creator` / `xmpRights:UsageTerms` / `xmpRights:WebStatement` / `plus:Licensor` の**文字列の有無**だけは低コストで検出できる。検出したら通常より強い警告にする（これらは利用条件そのもの＝定義ロに直球で当たり、③を満たす蓋然性が高い）。IPTC（APP13）は構造解析が高コストなので**「区画がある」ことだけ示す**
3. **警告は除去ボタンの直上に常時表示する。** 一度きりのトーストにしない（Winny最決が「常時…警告を発していた」ことを故意否定の事情として挙げている）
4. **検出した権利表示の値を画面に出し、コピーできるようにする。** 「消したら二度と戻らない」を回避する最小コストの手当て
5. **「自分が権利を持つ写真に使ってください」を入口（ファイル選択の近く）に置く**
6. **免責に「他人の著作物の権利表示を除去する目的で使用しないでください」を入れる**

## L. 書いてはいけない表現（画面・README・meta.json・SNS投稿文すべて）

- 「著作権表示を消して自由に使えます」「透かしを消せます」のような**侵害を促す表現**。汎用ツールから侵害誘導ツールへ性格が変わる
- 「このツールの利用は適法です」という**法的評価の断定**（③要件と除外事由に不明点が残るため）

## M. v1でやらないこと

- **「著作権表示だけを選択的に除去する」機能**（⚠️最重要の禁止事項）。ときめきメモリアル最判の「専ら…改変のみを目的とする」、平成24年改正解説の「その機能以外に実用的な意味をもたない」に触れる単能機能になる。**残す方向の選択肢は作ってよい。消す方向の選択肢は作らない**
- 「Exifの権利表示だけを残して他を消す」オプション（v2候補）。DESIGN.mdのペルソナ（写真を売っている人）が立っているので方向としては正しいが、1日の枠に入らない。**READMEに今後の候補として書く**。実装するときは「Exifの著作権表示だけを残します（XMP・IPTCの分は消えます）」と**容器名まで書く**こと。でないと嘘になる

# 追記4：別系統の調査から届いた補強（2026-08-18）

条番号を独立した2系統の調査が確認し、**どちらも 113条8項2号／2条1項22号 に到達した**。以下は片方だけが持っていた材料。

## N. 文化庁の公式資料による条番号の裏取り

文化庁著作権課『著作権テキスト －令和7年度版－』（https://www.bunka.go.jp/seisaku/chosakuken/seidokaisetsu/pdf/94283401_01.pdf ）**印刷ページ102**、「１４．著作権が『侵害』された場合の対抗措置／（３）著作権の侵害とみなされる行為」に次の記述がある。

> ⑨ 著作物等に付された「権利管理情報」（「電子透かし」などにより著作物等に付されている著作物等、権利者、著作物等の利用条件などの情報）を不正に、付加、削除、変更すること…（**第113条第8項**）

直前の印刷ページ101には113条の全項を並べた一覧表があり、そこにも「⑨権利管理情報の改変等（**第８項**）」とある。**文化庁自身が現行の項番号で振り直した公式資料**なので、条番号の根拠としてはe-Gov本文に次いで強い。

⚠️ **ただしこの記述は「電子透かしなど」を例示しており、ExifのCopyright/Artistには一切言及していない。条番号の裏取りには使えるが、Exif該当性の根拠にはならない。** 分けて扱うこと。

## O. 著作権法19条（氏名表示権）— 別ルートの論点

113条8項とは別に、**19条**が問題になりうる。ただし**射程が限定されている**ことが条文構造から読める。

19条1項が働くのは「その著作物の**原作品に**」表示する場面と、「その著作物の**公衆への提供若しくは提示に際し**」ての表示の2つ。つまり**公表・利用の局面の権利**であって、

- **手元のファイルから消して自分で保管するだけなら、公衆への提供も提示も起きていない＝19条の問題は生じない**と読める。このアプリの標準的な使い方はここに収まる
- リスクが立つのは「**消したうえで公開する**」局面。ただしそれは**利用者の公開行為**の問題で、ツールが除去した時点で完結する話ではない
- 19条3項に省略の余地がある（「著作者が創作者であることを主張する利益を害するおそれがない」かつ「公正な慣行に反しない」とき）。SNSがアップロード時にメタデータを一律に落とす現在の慣行との関係で、ここが効く余地がある

🔴 **未確認：Exifの `Artist` のような「ファイルに埋め込まれた氏名」が、19条にいう「著作者名の表示」に当たるかを正面から論じた裁判例・文化庁資料・学説は見つからなかった。** 条文の「原作品に…表示し」という文言は絵画の署名のような可視の表示を想起させるが、画面に見えないメタデータがこれに当たるかは不明。**「Exifの Artist を消すと氏名表示権侵害になる」とは断定できないし、「ならない」とも確認できていない。論点として存在することまでが確認できた事実。**

→ 実装への影響はない。既存の設計（`Copyright`/`Artist` を検出したら消す前に警告し、値をコピーできるようにする）が、この論点に対しても同じ方向を向いている。

## P. 責任制限条項を書く場合の要件（いまは書いていないので影響なし）

経産省『電子商取引及び情報財取引等に関する準則』令和7年2月版（https://www.meti.go.jp/files/900015316.pdf ）**印刷ページ53〜55**より。

**このアプリは責任制限の条項を1つも書いていない**（`lib/copy.js` にあるのは「何を保証しないか」という事実の記載だけ）。したがって現状は影響なし。**将来書くなら**次を守ること。

- 🔴 **上限額を書くなら「当社が軽過失の場合に限り」を明示しないと、上限条項ごと無効**（消費者契約法8条3項・令和5年6月1日施行）。「法律上許される限り、賠償限度額を〇万円とする」は無効例として明示されている
- 🔴 **「故意・重過失の場合は賠償する」という但書を付けても、軽過失を全部免責していれば無効**（東京高判平成29年1月18日）
- **有効例**：「当社の責めに帰すべき事由により生じた損害については、通常損害のみ責任を負い、特別損害については責任を負わない」（ただし故意・重過失があれば無効）
- 「当社が認めたときは全額賠償」のように**責任の限度を事業者が決める権限を与える条項は無効**
- **人身損害は、全部免責はもちろん一部制限も無効とされる可能性がある**
