### 難易度順序：改善を確認、良好なカーブの完成までは未証明

`lib/stages.js:1–82` と `app.js:412–426` は以下の順序で一致する。

### ボタン文言と判定：前の明示的保証は消えたが、意味の矛盾は残る

第4現場のボタンは「定期・補償なし」という明示的保証から、**「上記内容に同意して単品購入を確定」**へ変わった（`app.js:480–481`）。両注文ボタンは同じ `checkDamage` を呼び、残ったオプションに対応して課金する（534–553）。未解除の費用が表示金額と一致する点は改善として認める。

しかし「単品購入を確定」と表示して、チェックが残ると定期便へ申し込ませるのは依然として矛盾する。乱数を0に固定したVMでは **¥4,980 + ¥550 = ¥5,530**、0.99では **¥6,980 + ¥950 = ¥7,930** の被害を登録した。「上記内容に同意」は事前選択適用を示すが、「単品購入」を定期契約の意味へ変換する根拠にはならない。

これは故意の罠だとしても、成功・失敗の説明に必要な整合性の問題である。ボタン自体が嘘をつく教材なら、その嘘を解説し、安全に単品購入できる経路との違いを定義する必要がある。現在の解説は事前選択・抱き合わせのみを説明する。**完全解決とは判定しない。**

### 時間切れ：直後の判定は合格、結果と共有への伝達は不合格

`handleTimeout()`（`app.js:233–249`）は第1〜4現場の未確定を **被害¥0・ミッション未達**、第5現場の既存契約の未解約を **¥1,980・ミッション未達** とする。VMで全5現場のタイマー経由の確定を確認した。安全条件へ変更した第2〜4現場でも、未確定なら¥0・時間切れ失敗のまま。以前の未承諾・未予約・未開始への架空請求は解消された。

`showClearedModal()` は `!isTimeout && damage === 0` の場合だけ完全看破とし、時間切れは「時間切れ！ミッション失敗！」へ分岐する（289–307）。`finishGame()` も `hasTimeouts` をランクへ渡し、被害¥0でも時間切れがあればBにする（353–355）。この修正は実質的である。

一方、最終一覧は `damage === 0` だけで「¥0 (回避)」を表示し（378–385）、共有処理は `calculateRank()` に `hasTimeouts` を渡さない（391–398）。**直後の失敗 → 一覧の回避 → 共有の高ランクという不整合が残る。** 再現はTOP1参照。

### ランダム化：存在を確認、判断課題の変化は限定的

- 第1現場：有料メルマガの金額と×の挙動（`app.js:558, 600–605`）。
- 第2現場：年額と月額（824–825）。重要事項・安全スイッチ・正解文言と位置は固定。
- 第3現場：価格・閲覧人数・プラン順・初期選択（630–647）。
- 第4現場：定期／補償金額とオプション順（435–455）。確定ボタンの位置と判定は固定。
- 第5現場：アンケート順、最終ボタンの強調・順（725, 795–806）。質問と回答の意味は固定。

乱数0と0.99の二条件で、第4現場の金額とオプション順が変わることを実際の生成HTML・課金で確認した。単なる×移動だけだったCycle 2からの改善は明確。**飽き耐性は0点から1点へ。**

ただし、すべての問題を同じIDの拒否・安全選択・解除へ進めれば解ける構造は変わらず、価格が変わっても正解の判断原則や必要な比較はほぼ同じ。特に第3現場は先頭のradioが常に選択済みになる。順番の変更と難易度の変更が混ざっており、純粋に正解位置の暗記を防ぐ設計とは言い切れない。2周目の実体験や3分以上の飽き評価は未実施であり、2点は与えない。

## 4. 改善TOP5

### TOP1：時間切れ状態を最終一覧・共有まで保つ

**重要度：高。確認済みの機能不具合。**

再現条件：第1現場を20秒で時間切れにし、残り4現場を被害¥0で確定する。VMでは以後の操作時間を0秒とし、総操作時間は20秒。

| 出力先 | 現在の実出力 |
|---|---|
| 第1現場直後 | 時間切れ！ミッション失敗！ |
| 最終ランク | B：迷えるネット市民（時間切れ） |
| 第1現場の捜査記録 | ¥0 (回避) |
| X共有処理が生成する称号 | 特務UI捜査官（神の洞察眼）：S相当 |

原因：`finishGame()` は `hasTimeouts` を渡すが `shareToX()` は渡さない。`calculateRank()` の第3引数の初期値はfalse（`stages.js:85`）なので、時間切れ¥0でも45秒以内なら共有側だけSになる。45秒超ならAになる。共有の「クリア！」という文言も未達を区別しない。

共有関数の `window.open` はモックへ差し替えており、Xを開いたり外部送信したりしていない。ブラウザ表示は未確認だが、実関数が生成するURLの称号と最終DOMへ設定するランクの矛盾は確認済み。

**修正方針**：確定済みの結果を表示・一覧・共有で共用する。被害額とミッション達成状態を別に扱い、時間切れの一覧は「未完了・被害¥0」とする。

**受け入れ条件**：各現場で時間切れを含む周回に対し、モーダル・一覧・ランク・共有が同じ成績を示す。安全な全5現場成功時だけS/Aを許す。

### TOP2：「単品購入」と定期便適用を両立させない

**重要度：高。確認済みの文言と契約内容の矛盾。**

第4現場でチェックを残して「上記内容に同意して単品購入を確定」を押すと、定期便を含む¥5,530〜¥7,930を加算する。価格のランダム化自体は判定と一致している。問題は「単品」の意味。

**修正方針**：チェック状態を適用するなら「選択中の契約・オプションで注文を確定」など内容に合う文言にする。単品を保証するなら定期便解除を保証する処理にする。

**受け入れ条件**：定期／補償の4組み合わせと両注文ボタンで、提示した契約・内訳・請求が一致する。ダークパターンの教材という設定だけで判定矛盾を免責しない。

### TOP3：計時とリトライの採点規則を整える

**重要度：中。端数欠落は確認済み、時間精度の指摘はCycle 2から継続。**

`activePlaySeconds` は実時間の差分ではなく1秒intervalの発火回数（`app.js:213–215`）。各現場で900ms経過してtick前に確定する系列をVMで実行すると、操作相当4.5秒でも積算0秒、結果表示1秒になる。ブラウザの背景タブでどれだけずれるかは未検証であり断定しない。

解説60秒を除外する改善は今回も確認した。一方、リトライは被害と結果だけを取り消し、失敗した操作時間を残す（194–201）。ルール画面にその説明がない。速さをS/Aの根拠とするなら、時間精度とリトライの扱いは成績へ直結する。

**修正方針**：単調時刻の開始・停止差分でプレイ時間を累積し、解説を除外。やり直し時に取り消すもの・残すものを明記する。

**受け入れ条件**：各現場の端数を合算し、同じ実操作時間で解説を即閉じる場合と60秒読む場合の成績が一致する。リトライ後の時間・被害が説明した規則どおりになる。

### TOP4：ランダム化と段階的な学習を両立させる

**重要度：中。生成HTMLの問題を確認、飽きの実感は未確認。**

ホテルの順序を反転させる `isReversed` が初期選択にも使われ、常に先頭がcheckedになる。安全プランが先頭の回は予約ボタンだけで成功する。これを意図した易しい回にするなら、その位置付けを設計で明示すべきであり、すべての回で一定の難易度が実現したとは言えない。

金額・選択肢順・色の変化は認めるが、第1現場の拒否、第2現場の安全スイッチ、第4現場の両解除、第5現場の「はい／退会する」という解法は固定。価格を変えただけでは判断条件は増えない。

**修正方針**：順番と初期選択を別に設計し、意味を読む必要がある条件差を与える。簡単な第1現場から複数解除へ進む時間配分を実プレイで確認する。

**受け入れ条件**：少なくとも2周・3分以上の操作記録で、前回の位置や固定文言だけでは解けず、同じ原則を別条件に適用する場面を示す。金額表示と課金の一致も維持する。

### TOP5：回帰テストと最新の実操作証拠を追加する

**重要度：中。現在の成功テストで欠陥が見逃される。**

単体7件のうち今回追加された時間切れランクのケースは、関数へ明示的にtrueを渡すだけ。共有側が引数を渡し忘れる今回の欠陥を検出できない。既存E2Eも時間切れを含む周回を検証しない。撮影スクリプトは出力先・順序がCycle 2のままで、現在の第1現場で存在しない `#chk-opt-sub` を操作する（`tools/capture-harness-shots.mjs`）。Cycle 3の証拠収集にそのまま使えない。

**修正方針**：時間切れを含む周回の表示と共有の一致、全現場の安全／危険／未確定、両注文ボタン、端数計時、解説60秒、重複確定を回帰対象にする。最新順序で画面を撮影する。

結果モーダルは `screenGame` のinertと次へfocusを備えるが、focusトラップ・終了後の操作先へのfocus・`aria-modal` は未実装。引き留めミニダイアログにもfocus管理はない。これを実機で背景課金が起きた証拠とはしないが、Tab / Enter / Spaceでの確認が必要である。
