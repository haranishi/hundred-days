### H1【高】モーダルと結果画面のボタンの2回押しが、次の画面の偽サイトへ貫通する

- **場所**: `app.js:135-145`（次へ・やり直すの処理）、`app.js:215-219`（`closeModal` が `inert` をすぐ外す）、`app.js:282-302`（`loadStage` が同じ処理の中で次の偽サイトを描く）、`app.css:1927`（カットインは `pointer-events: none`）、`app.js:469-517`（`finishGame`）
- **何が問題か**: 1回目のクリックの処理の中でモーダルを消し、次の偽サイトを描きます。カットインは押下を素通しし、カットイン中の操作も受け付けます。そのため、2回目のクリックやタップは、同じ座標にある次の現場の部品に届きます。その結果は、カットイン中の確定として0ミリ秒で記録されます。
- **失敗シナリオ（実測。Chromium、各4〜6回）**:
  - 390×844、第3現場を突破して「次の現場へ進む」をダブルクリック → 2回目が第4現場の `#btn-stage1-subtle` に当たり、チェックが付いたままなので「TRAPPED!」¥5,530〜¥7,930（マウス6/6、タッチの2連打3/4）
  - 375×667、第2現場のあとで同じ操作 → 第3現場の `#btn-hotel-submit` に当たり、初期選択の返金不可プランで「TRAPPED!」¥18,000〜¥28,000（マウス6/6、タッチ4/4）
  - 375×667、第3現場のあとは、ボタンの真下が第4現場の `#btn-stage1-loud`（6/6）
  - 375×667、最後の解説の「捜査報告書を見る」をダブルクリック → 2回目が結果画面の `#btn-retry` に当たり、ランクも共有も見ないまま新しい周が始まる（4/4）
  - 375×667、第3現場の失敗後の「この現場をやり直す」の真下は `#btn-hotel-submit`（4/4）。2回押すと、やり直した直後にまた被弾する
  - 390×844、「捜査報告書を見る」の真下は結果画面の `#btn-share-line`（6/6）。ダブルクリックでLINEの画面が開くかは、今回の計測では確認できていない
  - 「捜査を開始する」のダブルクリックは、390・375・1440のどれでも何も起きない（8/8）
- **影響**: スマホで反応が遅いと感じて2回押すのはよくある操作です。UX5階層の戦略層が敵としている「原因が分からない失敗」そのものになります。
- **推奨**: 新しい画面を出した直後の短い間（300〜400ミリ秒）は、前の画面での押下の続きを受け付けないようにします。R2の決定3「カットイン中も操作はできる」とは、1秒のうち残りの600ミリ秒ほどで両立できます。

  ```js
  // 画面を出した直後だけ、前の画面で押した指の2回目を受け付けない
  const INPUT_GUARD_MS = 350;
  function guardInput(root) {
    root.inert = true;
    setTimeout(() => { root.inert = false; }, INPUT_GUARD_MS);
  }
  // loadStage の renderStageContent の直後に guardInput(stageViewport)、finishGame で guardInput(screenResult)
  ```

  時計を止めるE2E（`day-063.spec.mjs:185-205` の、カットイン中に確定する手順）は、確定の前に `page.clock.runFor(400)` を足す必要があります。カットイン中であることは変わらないので、積算0の検証は残せます。あわせて「390×844で第3現場のあと `#btn-next-stage` をダブルクリックしても第4現場が確定しない」「375×667で『捜査報告書を見る』をダブルクリックしても結果画面に留まる」のE2Eを足してください。

### M1【中・仕様の解釈が要る】時間切れの現場をやり直すと、時間切れが記録から消えてSやAが取れる

- **場所**: `app.js:304-313`（`retryCurrentStage` は直前の結果を種類を問わず取り除く）、`README.md:13`
- **何が問題か**: 不変仕様1は「時間切れは被害0円でも未達。最終一覧は `未達 (時間切れ)`、ランクは最高でもB」です。ところが、時間切れの解説から「この現場をやり直す」を押すと、時間切れの記録そのものが消えます。残るのは失った時間だけです。開始画面の「失敗した現場はやり直せます」とは合っています。一方、README の「時間切れは…その周のランクは最高でもBです」とは食い違います。このやり直しの経路を検査するテストはありません。
- **失敗シナリオ（実測。時計を止めて操作）**: 第1現場で20秒待って時間切れ（解説は「TIME UP! 時間切れ」）→「この現場をやり直す」→ 全現場をそれぞれ0.5秒で突破 → 結果は **ランクS・22秒**。一覧は5件とも「回避 ¥0」で `未達 (時間切れ)` は出ず、共有文も「ランクS」
- **推奨**: どちらにするかを本人に確認してください。
  - (a) いまの動きを正とするなら、README を「時間切れのまま次へ進んだ周は、ランクが最高でもB」に絞り、やり直し後にSが取れることをE2Eで固定する
  - (b) 不変仕様1を文字どおりに守るなら、周の状態に `hadTimeout` を持たせてやり直しでも消さず、`calculateRank`・一覧・共有文に渡す（自己ベストの対象外にもなる）

### M2【中・仕様の穴】カットインの1秒は計時されないのに操作できるため、準備がすべて無料になる

- **場所**: `app.js:322-337`、`app.js:347-350`。E2Eの `day-063.spec.mjs:185-205` がこの挙動を固定している
- **何が問題か**: 「カットイン中は計時しないが、操作はできる」というR2の決定3の組み合わせが、計時の抜け道になっています。偽サイトはカットインの下に描画済みで、押下も通ります。たとえば第4現場では、カットイン中に2つのチェックを外しておけば、計時されるのは最後の確定の一押しだけです。5現場ともカットイン中に確定すると合計0ミリ秒になり、表示は「1秒」（`Math.max(1, …)`）、ランクSで、自己ベストにも1秒が保存されます。
- **失敗シナリオ（コードからの推論。0ミリ秒の確定はE2Eで実証済み）**: 慣れた人ほどカットイン中に操作を済ませるようになり、Sの45秒と自己ベストは、読み解く力よりも各現場の最初の1秒の使い方を競うものになります。
- **推奨**: 決定3を覆す提案ではなく、判断材料として挙げます。たとえば「カットイン中に偽サイトの中で最初の入力があったら、その時刻から `activePlayMs` を数え始める（残り時間の表示はカットイン後に動かす）」とすれば、操作できることと残り時間が減らないことの両方を保てます。H1の入力ガードと同時に決めるのが効率的です。

### M3【中・テストの質】不変仕様3のE2Eは「回数ベースの実装」と「解説の時間を数える実装」を見分けられない

- **場所**: `tests/e2e/day-063.spec.mjs:185-205`、`:54-63`（`playWithClock`）
- **何が問題か**: 各現場を900ミリ秒で確定しています。900は表示更新の間隔 `TICK_MS = 100` の倍数です。そのため、`setInterval` の回数×100ミリ秒で数える実装でも合計は同じ3600になり、テストは通ります。また、解説モーダルを開いている間は `page.clock` が止まったままなので、解説を読む時間を合計に入れる実装でも3600のままです。不変仕様3の「回数ベースにしない」「解説を読む時間は含めない」の2点が、テストでは固定されていません。
- **失敗シナリオ（推論）**: 計時を `state.activePlayMs += TICK_MS`（tickごと）に戻しても、合計を「次へ」を押すまで止めない形に変えても、このE2Eは合格する。
- **推奨**: 100の倍数でない値（例: 937・1234・1501ミリ秒）で確定し、合計をミリ秒で一致させてください。解説モーダルを開いている間に `page.clock.runFor(10_000)` を挟み、合計が変わらないことも確かめてください。失敗した試行の時間が合計に残ることも、時計を止めた状態で1件足すと安心です。

### M4【中・テストの質】不変仕様2のE2Eは「目立つボタン＋チェックあり」と、チェックが片方だけの状態を見ていない

- **場所**: `tests/e2e/day-063.spec.mjs:341-362`
- **何が問題か**: 確かめているのは「目立たない確定ボタン＋チェック2つ → 被弾2件」と「目立つボタン＋チェックなし → ¥0」の2通りです。全現場突破のE2Eが「目立たない確定ボタン＋チェックなし → ¥0」を補っています。しかし「目立つボタン＋チェックあり」と、チェックが片方だけの状態は、どのテストも通りません。
- **失敗シナリオ（推論）**: `btnLoud` を常に ¥0 で確定する誤り、または配送補償のチェックを無視する誤りが入っても、全テストが通る。
- **推奨**: 「目立つボタン＋チェック2つ → 被弾2件」と「配送補償だけチェック → 被害額が配送補償の額と一致」を足し、被害額が内訳の合計と一致することも確かめてください。

### M5【中・UXとアクセシビリティ】375×667では、解説モーダルの2ボタンがモーダル内のスクロールの下に隠れる

### 見て問題がなかった観点

- **XSS**: `innerHTML` に入る文字列は、すべて内部の定数か数値です。文字列は `escapeHtml` を通しています（称号の `<wbr>` もエスケープの後で足している）。`localStorage` の値は `parseBest` が整数とS・Aだけに絞り、`textContent` で出します
- **CSP**: インラインscript、`on*=` 属性、`style=` 属性、`eval` はありません。スタイルの変更はCSSOM経由です
- **外部通信**: `fetch` などはありません。X・LINEは押したときの画面遷移だけです。共有URLは `encodeURIComponent` で組み立て、canonical が無ければ `location.href` を使います
- **`localStorage` の例外**: getter・`getItem`・`setItem` をすべて try/catch で囲んでいます。拒否されてもページ内の記録で比べます（E2Eあり）
- **二重確定**: `stageResolved` の確認と、モーダル表示時の `inert` で二重に防いでいます。時間切れと確定が同時でも、先に来た方だけが記録されます
- **共有ダイアログ**: 捜査中は開けず、Escと「閉じる」で開いたボタンへフォーカスが戻ります。`.share` は1つです
- **変種の選択**: `pickVariant` は直前の番号を除いて等確率で選び、壊れた乱数でも範囲内に収まります。`state.variants` は周をまたいでも保たれます
- **自己ベスト**: 対象の判定・更新の判定・保存の形（秒数とランクだけ）・壊れた値の扱い
- **CSS**: 未使用のクラスと変数はありません（動的に組む `flash-*`・`is-*` も確認済み）。`[hidden]` を `display` で上書きしている箇所は、それぞれ `[hidden]` の規則を足してあります
- **privacy.html・meta**: 追記は「端末内への保存」節の中にあり、最終改定日の行の書き方も前例に合っています。`meta.json` の「全5問」は実装者が報告済みです
