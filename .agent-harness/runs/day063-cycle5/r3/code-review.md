### 中2 文節化の `<wbr>` と糊付けの span が、VoiceOver（iPhone）で文を細切れに読ませるおそれ（推測）

- **場所**: `lib/phrase.js:195-265`、`app.js:61-69`（画面の文字はすべて `setText`・`setHTML` を通る）
- **何が問題か**: `phrasifyNode` は文を文節ごとの文字ノードに切り、記号のまわりを span で包みます。開始画面の見出しは `ネットに<wbr>潜む<wbr><span data-ph>「罠</span>U<span data-ph>I」を</span><wbr>看破せよ` になります（最小DOMで確認）。iOS の VoiceOver には、行内の要素で区切られた文字を別々の項目として読む癖が知られています（WebKit 独自の `role="text"` でまとめる回避策があるのはこのため）。この癖が `<wbr>` と span にも出るなら、見出しは「ネットに」「潜む」「「罠」「U」「I」を」「看破せよ」の6回のスワイプに分かれます。ボタンとリンクの読み上げ名は1つにまとまるので、影響は見出し・段落・解説・結果の文にかぎられます。
- **失敗シナリオ（推測・未確認）**: iPhone で VoiceOver をオンにして開始画面を右スワイプで読むと、見出しとルール欄が文節ごと・記号ごとに止まり、解説モーダルの「心理誘導のメカニズム」は数十回のスワイプになります。
- **推奨**: まず実機（または Mac の VoiceOver と Safari）で、開始画面の見出しと解説モーダルを1回ずつ読ませて確かめます。細切れになるなら、操作部品を含まない入れ物（`h2`、`.intel-val`、`.rank-details p` など）の中身を `<span role="text">` で包む案と、糊付けの span を減らして `<wbr>` だけにする案を比べます。どちらにしても4幅のレイアウト検査を流し直してください。

### 低3 `phrasifyNode` の後片付けが、触らないはずの要素にも及ぶ

- **場所**: `lib/phrase.js:277-279`（ルートの中の `<wbr>` をすべて外し、糊付けを解いて `normalize()`）、説明は `:267-272`
- **何が問題か**: 説明には「script・style・textarea・[data-no-phrase] の中は触らない」とありますが、後片付けは飛ばす要素の中にも効きます。最小DOMで `<p data-no-phrase>区切らない<wbr>文</p>` を通すと `<wbr>` が消えました。nowrap の中に書いた `<wbr>` も消えます。いまのアプリには `[data-no-phrase]` も nowrap の中の `<wbr>` もないので、画面への影響はありません。
- **推奨**: 後片付けの対象から、飛ばす要素の中を除きます（`closest(SKIP_SELECTOR)` で判定）。E2E「文節の区切り（phrasifyNode）」の `#t-skip` に `<wbr>` を1つ入れておけば固定できます。

### 低4 `data-phrased` が `#app` 全体に付き、文節化していない文字まで keep-all と anywhere になる

- **場所**: `app.js:147`（`phrasifyNode(appRoot)` が `#app` に属性を付ける）、`app.css:53-57`（3つとも継承するプロパティ）

- **推奨**: README の「作りの特徴」に「flex の直下と nowrap の中は文節化しない。そこには短い文言だけを置く」と1行足します。
